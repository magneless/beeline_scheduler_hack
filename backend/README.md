# Backend

Требуется Go 1.27. `planner.New()` реализует `contracts.Planner` и выбирает режим по `SolveRequest.Mode`:

- `baseline` — жадный алгоритм по `source_order`, затем ID;
- `optimized` — OR-Tools Routing Solver 9.15 через Go-обёртку Airspace;
- `insert_only` — проверка всех допустимых зазоров для одной новой обычной заявки с сохранением старых назначений.

Также доступны `NewBaseline()`, `NewOptimized()` и `NewInserter()`. Входные структуры не изменяются; каждый вызов владеет своим состоянием. Начатую работу и историю сохраняет вызывающий модуль Go-4.

В объединённом backend также находятся PostgreSQL storage, DEMO_GEO provider, PlanService и HTTP server; это один Go-модуль `github.com/magneless/beeline_scheduler_hack/backend`.

Диспетчерский API (`/api/v1`) строит варианты через `POST /scenarios/{id}/proposals`, отдаёт актуальный непринятый набор через `GET /scenarios/{id}/proposals/current` и фиксирует выбранный вариант через `POST /proposals/{id}/accept`. До принятия расчёт не меняет рабочий план. Начало дня предлагает строгое соблюдение окон и допуск опоздания на аварии. При аварии добавляется вариант с резервом; при остальных событиях доступны расчёты работающим составом и с резервом, а также сохранение прежнего расписания. Сравнение включает маршруты, изменения назначений, неназначенные заявки с причинами, опоздания, состав инженеров и пробег. Правила — в [рабочем процессе диспетчера](../docs/dispatcher-flow.md) и [перерасчёте при событиях](../docs/route-recalculation.md).

Резерв определяется при принятии первого плана: доступные бригады без заданий переходят в резерв. Завершившие работы бригады остаются в рабочем составе. В CSV необязательная устаревшая колонка `reserve` принимает только `false`; ручное назначение резерва запрещено. При принятии варианта с резервом только задействованные бригады возвращаются в работающий состав.

Реализации и их тесты разделены на пакеты:

- `internal/planner/baseline` — жадный алгоритм, конструктор `baseline.New()`;
- `internal/planner/optimized` — OR-Tools Routing, конструктор `optimized.New()`;
- `internal/planner/internal/shared` — общие проверки входа и допустимости маршрутов;
- `internal/planner` — выбор режима и `insert_only`.

Общие тестовые данные находятся в `internal/planner/internal/testutil`.

## Сборка и проверки

Команды выполняются из `backend`.

Для `baseline` и `insert_only` нативная библиотека не нужна:

```bash
go test -race ./...
go vet ./...
```

Для `optimized` нужны включённый cgo, C-компилятор и Linux-библиотеки `libgoortools.so` / `libortools.so`. Подготовка и полный набор тестов:

```bash
./scripts/setup-ortools.sh
./scripts/test-ortools.sh -race -count=1
```

Установщик поддерживает Linux x86_64 и aarch64 и размещает библиотеки в `.cache/ortools/lib`.

Сборка и статическая проверка с OR-Tools:

```bash
export CGO_ENABLED=1
export CGO_LDFLAGS="-L$PWD/.cache/ortools/lib -Wl,-rpath,$PWD/.cache/ortools/lib"
export LD_LIBRARY_PATH="$PWD/.cache/ortools/lib${LD_LIBRARY_PATH:+:$LD_LIBRARY_PATH}"
go build -tags ortools ./...
go vet -tags ortools ./...
```

Без build tag `ortools` вызов `optimized` возвращает `COMPUTATION_FAILED`.

## Docker и Compose

Из корня репозитория:

```bash
docker compose --profile test run --rm --build backend-test
```

Тестовый контейнер запускает набор тестов с `-race`, включая `optimized`, и использует PostgreSQL из compose через `TEST_DATABASE_URL`; runtime backend запускается отдельным сервисом compose.

Дополнительные команды:

```bash
docker compose --profile test run --rm backend-test go vet ./...
docker compose --profile test run --rm backend-test go test -run TestOptimized -count=1 ./...
```

## Модель optimized

Поиск выполняется последовательно по шести критериям контракта: число аварий, подключений, ремонтов/дозаказов, задержка начала аварий, число использованных инженеров, расстояние. Каждый следующий этап фиксирует достигнутые количества и ограничивает ранее достигнутые минимизируемые метрики сверху. Нижние приоритеты не могут ухудшить выбранный план по верхним. Большие веса для кодирования всей иерархии не используются.

Первое решение строится `PARALLEL_CHEAPEST_INSERTION`, улучшение — `GUIDED_LOCAL_SEARCH`. Допустимый baseline используется как начальный кандидат. Каждый найденный маршрут заново проверяется и получает самое раннее допустимое расписание; кандидаты сравниваются по точной иерархии и правилу разрешения равенства из контракта. Для static travel matrices это не ухудшает ни допустимость, ни задержку аварий.

Время, смены и оборудование заданы через dimensions. Разрешённые инженеры определяются навыками, транспортом и остатком оборудования. Недостижимые плечи запрещены временной моделью. Конечный фиктивный узел имеет нулевую дорогу: возвращение в офис не добавляется. Дополнительное CP-ограничение связывает время выезда с `received_at` следующей заявки. CP-SAT fallback выключен, поскольку его routing-перевод не переносит эти произвольные CP-ограничения.

`time_limit_ms` включает подготовку и поиск; оставшееся время делится между этапами. При исчерпании бюджета возвращается лучший уже проверенный план, а все остальные заявки перечисляются в `unassigned`. Отмена контекста возвращает `ctx.Err()` без пригодного для сохранения результата. `completed` не означает доказанную оптимальность. Эвристический поиск и фиксация достигнутых значений не гарантируют глобальный лексикографический оптимум. Проверки диапазонов `int64` возвращают `COMPUTATION_FAILED` для численных значений, которые небезопасны для native модели.

## Вставка обычной заявки

`insert_only` проверяет исходные фиксированные маршруты, затем перебирает инженеров и зазоры. Сохраняются исполнитель, прибытие, начало, конец и порядок старых визитов. При вставке перед старым визитом время выезда рассчитывается назад от его сохранённого прибытия. Защищённый первый участок сохраняется дословно, даже если уже частично пройден или новая матрица изменилась; вставка перед ним запрещена. Свободные инженеры рассматриваются как пустые маршруты.

При таймауте возвращается исходный `fixed_routes` и новая заявка с `NOT_ASSIGNED_BY_SOLVER`. `NO_FEASIBLE_INSERTION` выдаётся только после проверки всех зазоров. Противоречивый старый план отклоняется как `INVALID_INPUT`; согласно контракту Go-4 должен обнаружить такой конфликт до вызова планировщика.
