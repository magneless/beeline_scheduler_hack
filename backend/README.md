# Backend

Требуется Go 1.27. `planner.New()` реализует `contracts.Planner` и выбирает режим по `SolveRequest.Mode`:

- `baseline` — жадный алгоритм по `source_order`, затем ID;
- `optimized` — VROOM 1.15 с адаптером на Go и локальным улучшением маршрутов;
- `insert_only` — проверка всех допустимых зазоров для одной новой обычной заявки с сохранением старых назначений.

Также доступны `NewBaseline()`, `NewOptimized()` и `NewInserter()`. Входные структуры не изменяются; каждый вызов владеет своим состоянием. Начатую работу и историю сохраняет вызывающий модуль Go-4.

В объединённом backend также находятся PostgreSQL storage, DEMO_GEO provider, PlanService и HTTP server; это один Go-модуль `github.com/magneless/beeline_scheduler_hack/backend`.

Диспетчерский API (`/api/v1`) строит варианты через `POST /scenarios/{id}/proposals`, отдаёт актуальный непринятый набор через `GET /scenarios/{id}/proposals/current` и фиксирует выбранный вариант через `POST /proposals/{id}/accept`. До принятия расчёт не меняет рабочий план. Начало дня предлагает строгое соблюдение окон и допуск опоздания на аварии. При аварии добавляется вариант с резервом; при остальных событиях доступны расчёты работающим составом и с резервом, а также сохранение прежнего расписания. Сравнение включает маршруты, изменения назначений, неназначенные заявки с причинами, опоздания, состав инженеров и пробег. Правила — в [рабочем процессе диспетчера](../docs/dispatcher-flow.md) и [перерасчёте при событиях](../docs/route-recalculation.md).

Резерв определяется при принятии первого плана: доступные бригады без заданий переходят в резерв. Завершившие работы бригады остаются в рабочем составе. В CSV необязательная устаревшая колонка `reserve` принимает только `false`; ручное назначение резерва запрещено. При принятии варианта с резервом только задействованные бригады возвращаются в работающий состав.

Реализации и их тесты разделены на пакеты:

- `internal/planner/baseline` — жадный алгоритм, конструктор `baseline.New()`;
- `internal/planner/optimized` — VROOM и локальный поиск, конструктор `optimized.New()`;
- `internal/planner/internal/shared` — общие проверки входа и допустимости маршрутов;
- `internal/planner` — выбор режима и `insert_only`.

Общие тестовые данные находятся в `internal/planner/internal/testutil`.

## Сборка и проверки

Команды выполняются из `backend`.

Сборка Go не требует cgo, специальных build tags или линковки с решателем:

```bash
CGO_ENABLED=0 go build ./cmd/server
go vet ./...
go test -race ./...
```

Для расчётов `optimized` нужен исполняемый файл **VROOM 1.15** в `PATH` либо путь в `VROOM_BIN`. Он включён в Docker-образ. Для локальной установки используйте [инструкции VROOM](https://github.com/VROOM-Project/vroom/tree/v1.15.0#solving-engine). Данные передаются процессу через stdin/stdout; отдельный HTTP-сервис VROOM и Python не нужны. При отсутствии исполняемого файла расчёт возвращает `COMPUTATION_FAILED` с инструкцией по установке.

Обычный `go test` проверяет модель, обработку ошибочных ответов, отмену и завершение дочернего процесса через тестовый исполняемый файл. Проверки с реальным VROOM включаются тегом **тестов** `vroom`:

```bash
VROOM_BIN=/path/to/vroom ./scripts/test-vroom.sh -race -count=1
go vet -tags vroom ./...
```

Для интеграционных проверок HTTP и хранилища задайте `TEST_DATABASE_URL` с отдельной тестовой PostgreSQL. Без неё соответствующие тесты пропускаются.

## Docker и Compose

Из корня репозитория:

```bash
docker compose up --build -d
docker compose --profile test run --rm --build backend-test
```

Backend собирается без cgo. Исполняемый файл VROOM берётся из официального образа `ghcr.io/vroom-project/vroom-docker:v1.15.0`; среда выполнения содержит только Go-сервер, VROOM и нужные ему библиотеки. Тестовый образ дополнительно содержит Go и C-компилятор для `-race`. Он запускает все тесты с тегом `vroom` и PostgreSQL из Compose.

```bash
docker compose --profile test run --rm backend-test go vet ./...
docker compose --profile test run --rm backend-test go test -run TestOptimized -count=1 ./...
```

`SOLVER_MODE=optimized` выбирает VROOM. `SOLVER_TIME_LIMIT_MS` задаёт общий бюджет одного поиска, по умолчанию **10000 мс**. `VROOM_BIN` позволяет указать путь к исполняемому файлу при локальном запуске; в контейнере используется `/usr/local/bin/vroom`.

## Модель optimized

Рабочий режим сочетает VROOM и расширенный локальный поиск на Go. Около 40% общего бюджета отводится построению кандидатов в VROOM с двумя потоками и уровнем поиска 5. Этапы добавляют аварии, подключения, затем ремонты/дозаказы. Уже назначенным работам передаётся высокий приоритет. Отдельный кандидат с более ранними окнами аварий помогает уменьшить задержку их начала; исходные окна не изменяются.

Навыки и требуемый транспорт передаются через `skills`, остатки роутеров и TV-приставок — через `capacity` и `delivery`. Для автомобиля и пешего транспорта передаются свои матрицы времени и расстояний. Стоимость использования новой бригады выше возможного пробега; у уже использованных бригад она равна нулю. Недостижимые плечи получают длительность больше всего горизонта. У маршрутов есть старт, но нет обязательного возврата в офис.

VROOM не выражает всю иерархию целей диспетчера или правило выезда после `received_at`. Поэтому ответ сначала проверяется на неизвестные, повторные и потерянные заявки. Затем Go заново рассчитывает самое раннее допустимое расписание. Визиты, нарушающие правила, исключаются из кандидата и остаются в `unassigned`; последующие участки проверяются заново. Оставшийся бюджет получает LNS: перестановки и вставки могут вернуть эти заявки. Все кандидаты сравниваются по точной иерархии контракта: число аварий → подключений → остальных работ → задержка аварий → число бригад → пробег → правило разрешения равенства. При `emergency_first=true` задержка аварий сравнивается перед числом обычных работ. Приоритет VROOM сам по себе не считается гарантией этой иерархии.

`time_limit_ms` включает подготовку, процессы VROOM и локальный поиск. При внутреннем таймауте сохраняется лучший проверенный кандидат. Отмена контекста останавливает и ожидает завершения дочернего процесса, затем возвращает `ctx.Err()` без плана для сохранения. Ошибка запуска, сбой процесса или неверный ответ дают `COMPUTATION_FAILED`. Параллельные вызовы имеют независимые процессы и состояние. Недопустимые для uint16/uint32 VROOM размеры, времена и стоимости отклоняются явно.

Завершение ограниченного локального поиска помечается `time_limit`. Пустая задача может завершиться с `completed`; этот статус не доказывает оптимальность. VROOM и LNS остаются эвристиками: найденный план допустим, но глобальный лексикографический оптимум не гарантируется.

## Вставка обычной заявки

`insert_only` проверяет исходные фиксированные маршруты, затем перебирает инженеров и зазоры. Сохраняются исполнитель, прибытие, начало, конец и порядок старых визитов. При вставке перед старым визитом время выезда рассчитывается назад от его сохранённого прибытия. Защищённый первый участок сохраняется дословно, даже если уже частично пройден или новая матрица изменилась; вставка перед ним запрещена. Свободные инженеры рассматриваются как пустые маршруты.

При таймауте возвращается исходный `fixed_routes` и новая заявка с `NOT_ASSIGNED_BY_SOLVER`. `NO_FEASIBLE_INSERTION` выдаётся только после проверки всех зазоров. Противоречивый старый план отклоняется как `INVALID_INPUT`; согласно контракту Go-4 должен обнаружить такой конфликт до вызова планировщика.
