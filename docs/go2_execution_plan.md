# План выполнения Go-2 по актуальным контрактам

Основание: [распределение работы](work_breakdown.md), [функциональный состав](functional_scope.md), [спецификация с QA](specification.md), [data.md](contracts/data.md), [common.md](contracts/common.md), [frontend.md](contracts/frontend.md), [plans.md](contracts/plans.md), [geo.md](contracts/geo.md), [planner.md](contracts/planner.md), сводки QA и примеры контрактов. Состояние репозитория проверено 23.09.2026.

После составления плана реализован backend Go-2 с PostgreSQL в ветке `codex/go2-data-infrastructure`. Запуск, выполненные проверки и ограничения заглушек описаны в [go2_backend.md](go2_backend.md). Раздел «Исходное состояние» ниже фиксирует состояние до реализации. Интеграция с реальными Go-3/Go-4 и согласование модельных настроек остаются отдельными задачами.

## Исходное состояние

- Уже есть Go-модуль, `internal/planner` с baseline и тестами, `internal/contracts/planner.go` с заявками, инженерами, оборудованием, маршрутами и общей ошибкой.
- Пока нет точки запуска сервера, HTTP API, импорта, хранилища и исполнителя асинхронных команд. Нет реализаций Go-3 и Go-4. Режим `optimized` текущий планировщик отклоняет.
- Имеющийся `go2_implementation_plan.md` устарел относительно контрактов: оборудование и статусы уже обязательны; событий четыре; аварийная работа занимает 4800, а не 6000 секунд; время источников московское; контрольные наборы исключены из экспериментов. Этот файл оставлен без изменений.
- В трёх синтетических CSV разделитель `;`, есть пустые строки и отдельная строка офиса в конце. У «Востока» есть дополнительная колонка «Подключение»; встречаются варианты «Адрес Офиса» и «Адрес офиса». ВК/HD содержат неоднозначные сочетания, например «Глобальная проблема / Информация» и «Дозаказ / Конвергенция абонента».

## Границы задачи

Go-2 отвечает за импорт и нормализацию, подготовленные региональные наборы, неизменяемые снимки, сохранение планов и событий, редактирование инженеров, девять HTTP-методов, запуски расчётов и сборку приложения.

Go-2 вызывает `Geocoder.Geocode` Go-3 при импорте и `PlanService.Build/Replan` Go-4 при расчёте. Go-4 получает от Go-2 `GetSnapshot/GetPlan`, возвращает `PlanResult`, после чего Go-2 вызывает собственный `CommitPlan`. Прямого вызова планировщика Go-1 из Go-2 нет.

Переходы фактических статусов, расход оборудования, допустимость маршрутов и метрики рассчитывает Go-4 совместно с Go-1. Go-2 проверяет вход HTTP, версии и целостность сохранения, хранит полученные факты и результаты. `equipment_remaining` сохраняется без повторного расчёта. Обед, ручное переназначение, полный складской учёт и внешние системы диспетчеризации в этот план не входят.

- [ ] Зафиксировать для каждого набора офис, timezone, состав инженеров, смены, навыки, транспорт и запасы. Недостающие свойства моделировать воспроизводимо; региональные составы не смешивать.

Уже определённые правила не требуют нового согласования: время CSV московское; `region_id` не выводится из административного столбца; для исходных заявок без времени поступления применяется документированное начало местного дня; для новой аварии — время события. Исторические статусы не становятся фактами нового дня.

**Готовность:** общие типы компилируются вместе с baseline; выбранные объекты из JSON-примеров читаются без потери контрактных полей; открытые решения по данным записаны отдельно от обязательных правил.

## 3. Реализовать постоянное хранилище и атомарный CommitPlan

По решению владельца Go-2 используется PostgreSQL с миграциями и драйвером pgx: служебные ключи и версии в колонках, контрактные снимки и планы — JSONB. Очередь запусков хранится в той же БД; отдельный брокер не нужен. Состояние реализации и запуск описаны в [go2_backend.md](go2_backend.md).

- [ ] Хранить сценарий с текущей ревизией и планом; снимки с уникальностью `(scenario_id, revision)`; планы; события; запуски; исходное нормализованное содержимое команд и ключи повторов; сведения о версии маппинга импорта.
- [ ] Создание сценария: ревизия 1, `current_plan_id=null`. Невалидный импорт не оставляет частично созданного сценария.
- [ ] `GetSnapshot` возвращает только запрошенную ревизию; отсутствующая — `NOT_FOUND`. В памяти не отдавать изменяемые ссылки на сохранённые карты и срезы.
- [ ] При чтении старого `ScenarioView` снимок старый, но `current_plan_id` отражает актуальный указатель сценария, как определено в примерах.
- [ ] PATCH атомарно проверяет `expected_revision` и блокировку редактирования, создаёт следующую ревизию. Старые снимки и планы сохраняются; событие старого плана после PATCH требует нового Build.
- [ ] `CommitPlan` сначала проверяет повтор команды, затем одновременно ожидаемую ревизию и текущий план. Несовпадение — `STALE_VERSION`.
- [ ] Проверять принадлежность сценарию, связь draft/target_snapshot, тип команды и применённого события. Для Build снимок должен совпадать с исходным; ревизия не увеличивается. Для Replan новая ревизия равна исходной + 1 и совпадает с ревизией draft.
- [ ] В одной транзакции сохранить событие и новый снимок при Replan, план с присвоенным ID, актуальные указатели и `Run=succeeded` с `plan_id`. При ошибке откатить весь результат.
- [ ] Сохранять геометрию, метрики, изменения, фактические статусы и остатки оборудования целиком. Не воспроизводить маршрутный валидатор Go-4 в хранилище.

**Готовность:** конкурирующие команды не перезаписывают друг друга; сбой в середине записи не меняет текущий снимок и план; старые версии читаются после перезапуска.

## 4. Сделать надёжные асинхронные запуски

- [ ] При приёме команды атомарно сохранить вход и зарегистрировать Run. Ключи: `(scenario_id, request_id)` и дополнительно `(scenario_id, event.id)` для события.
- [ ] Сравнивать нормализованное содержание команды, включая базовый план и исходную ревизию; порядок ключей JSON не должен создавать ложный конфликт.
- [ ] Повтор с тем же содержимым возвращает прежний `run_id` во всех состояниях. Другое содержимое — `IDEMPOTENCY_CONFLICT`. Дедупликация должна предшествовать отказу из-за версии, изменившейся после успешного первого выполнения.
- [ ] Выполнять `queued → running → succeeded/failed`. Рабочий context не связывать со временем жизни HTTP-запроса, который уже получил 202.
- [ ] Вызвать Go-4 вне транзакции БД, затем `CommitPlan`. Проверки при приёме команды не заменяют повторную проверку версий при сохранении.
- [ ] Ошибку после 202 помещать в `Run.error`; `GET /runs/{id}` при этом возвращает 200. Не менять бизнес-данные при ошибке Go-4 или геосервиса.
- [ ] Повтор failed-команды возвращает старую ошибку; новая попытка требует нового `request_id`, для события также нового `event.id`.
- [ ] Определить восстановление после перезапуска. Предложение: возвращать сохранённые queued в очередь, прерванные running завершать как failed с понятной причиной; уже сохранённый успех не переисполнять. Зафиксировать однопроцессный режим первой версии.

**Готовность:** параллельные одинаковые запросы дают один запуск и один эффект; ошибка сохранения не выдаётся как успех; зависшие запуски не остаются running бессрочно.

## 5. Реализовать полный импорт трёх синтетических наборов

- [ ] Поддержать известные варианты заголовков и кодировок, разделитель `;`, пустые строки и строку офиса вне основной таблицы. Контрольные файлы не включать в демокаталог и эксперименты.
- [ ] Проверять ID и дубли, адреса, даты и окна, классификаторы, нормативы; назначать стабильные ID и `source_order` исходных заявок.
- [ ] Обрабатывать ВК/HD совместно, не превращая одну строку в две заявки. `priority=urgent` только для `emergency`.
- [ ] Нормализовать московское время в UTC, сохраняя местную дату сценария; применять зафиксированное правило поступления исходных заявок.
- [ ] Подставлять инженеров и нормативы из региональных настроек, включая `equipment_stock` и `equipment_required` с кодами `router/tv_box`. Неизвестные коды и отрицательные количества отклонять.
- [ ] Вызвать геокодирование для адресов без координат и сопоставить ответы по `location_id`, а не по порядку. Проверить пропущенные, повторные и неизвестные ID ответа.
- [ ] Ошибки отдельных строк и адресов помещать в `Snapshot.issues` с номером строки, полем и причиной; непригодные заявки не включать в расчёт. Сохранять исходные строки для диагностики внутри импорта.
- [ ] Нечитаемый CSV или отсутствие корректного офиса не создаёт готового сценария. `GEO_UNAVAILABLE` всего вызова не превращается в ошибки всех адресов.
- [ ] Сохранять версию маппинга и модельных настроек для воспроизводимости.

**Готовность:** каждый из трёх наборов создаёт независимый сценарий; каждая строка учтена как заявка, служебная строка или объяснимая ошибка; результат воспроизводим при тех же настройках и ответах геокодирования.

## 6. Завершить HTTP API и поддержку событий

Все пути имеют префикс `/api/v1`.

| Методы | Что проверить |
|---|---|
| `GET /demo-datasets`, `POST /scenarios` | Каталог синтетических наборов, создание ревизии 1 |
| `POST /scenarios/import` | multipart `file/region_id/date`, частичные ошибки строк |
| `GET /scenarios/{id}` | Текущая или точная запрошенная ревизия |
| `PATCH /scenarios/{id}/engineers/{engineer_id}` | Конкурентное редактирование и ограничения дня |
| `POST /scenarios/{id}/plans` | Регистрация Build и ответ 202 с `run_id` |
| `POST /plans/{id}/events` | Сценарий берётся из сохранённого плана URL |
| `GET /runs/{id}`, `GET /plans/{id}` | Состояние запуска и полный сохранённый результат |

- [ ] В PATCH различать отсутствие поля и `null`: отсутствие не меняет значение, `null` запрещён, `skills=[]` допустим.
- [ ] Блокировать Build/PATCH, если текущий план имеет `base_plan_id != null`, любое `execution != null` либо `as_of` позже начала местного дня. Проверить первое событие ровно в 00:00 и исходную отменённую заявку без execution.
- [ ] Принять все четыре события: `urgent_order_added`, `order_cancelled`, `engineer_unavailable`, `order_status_changed`. Проверять форму payload, передавать бизнес-проверки и применение Go-4.
- [ ] Не добавлять отдельную команду завершения заявки: подтверждение статуса проходит через общий endpoint событий и атомарный CommitPlan.
- [ ] Не закрывать работы по времени плана. `EXECUTION_STATE_REQUIRED` возвращать в issues сохранённого плана, не превращать в failed-запуск.
- [ ] Соблюсти статусы ошибок: 400 — формат, 422 — недопустимые значения, 404 — отсутствие, 409 — конфликты, 503 — геосервис, 500 — сбой расчёта/недопустимый результат.

**Готовность:** девять методов совместимы с [frontend_flow.json](contracts/examples/frontend_flow.json), включая null/пустые коллекции, ошибки, повторы, статусы и оборудование.

## 7. Проверки, интеграция и поставка

Приоритетные тесты Go-2:

- [ ] Импорт: варианты CSV, офис в конце, неизвестная пара ВК/HD, дубли, неправильная дата/окно, частичная ошибка адреса и сбой всего геосервиса; авария 4800 секунд; нормативная дорога вычитается один раз.
- [ ] Хранение: точная старая ревизия, неизменяемость снимков, PATCH с устаревшей версией, атомарный откат на ошибке записи, сохранность после перезапуска.
- [ ] Гонки: одновременные повторы, повтор после успеха/ошибки, одинаковый ключ с разным телом, конфликт по event.id, две разные команды на одной исходной версии — сохраняется только одна.
- [ ] HTTP: все девять методов, 400 против 422, PATCH отсутствующее/null/пустое, ошибки после 202 через Run, блокировки после первого события.
- [ ] Интеграция с Go-4: Build без новой ревизии; каждый успешный статус/событие — ровно +1; расход при первом in_progress, без повторного списания на completed или обновлении оценки; отмена начатой работы не возвращает оборудование.
- [ ] Проверить сохранение предупреждения при неизвестном/истёкшем `expected_end_at`, истории выполненного и старой геометрии. Ответственность за бизнес-расчёт этих значений остаётся у Go-4.
- [ ] Подключить реальные Go-3 и Go-4. Полное сравнение baseline/optimized зависит от реализации optimized Go-1; заглушка не является завершённой интеграцией.
- [ ] Выполнить `go test ./...`, `go vet ./...`, `go test -race ./...` в поддерживаемой среде.
- [ ] Дополнить README: запуск, конфигурация, хранение, три демонабора, нормативы, маппинг, допущения и демонстрационный сценарий. Общую сквозную проверку провести с Go-4.

**Готовность:** приложение запускается по README; сценарий «импорт → Build → факт выполнения/новая авария/отмена/недоступность → новый план → чтение истории» работает с реальными зависимостями; ошибки и повторы не повреждают данные.

## Порядок небольших поставок

1. Общие типы и интерфейсы, каркас, заглушки.
2. Минимальное хранилище и демонабор, Build через HTTP, чтение Run/Plan/Snapshot — первая интеграция с Frontend.
3. Транзакционный CommitPlan, идемпотентность, конфликты и восстановление запусков.
4. Региональные настройки, полный импорт и PATCH инженеров.
5. Все четыре события, фактические статусы и оборудование в API/хранении, проверки блокировок.
6. Реальные зависимости, проверки ошибок и гонок, README и демонстрация.

Самая рискованная часть Go-2 — согласованное сохранение снимка, события, плана и Run при повторах и конкуренции. Её стоит закончить до массового подключения событий. Подготовку полного импорта можно вести после первого HTTP-сценария, не задерживая Frontend. Сроки в днях здесь не назначены: дедлайн и доступное время участника неизвестны.
