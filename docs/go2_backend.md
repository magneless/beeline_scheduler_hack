# Go-2: запуск и интеграция

> Этот документ сохраняет описание исходного Go-2 слоя. Сейчас весь backend объединён в `backend/`, а актуальный совместный запуск описан в [integration.md](integration.md).

Реализованы PostgreSQL-хранилище, миграции, импорт синтетических CSV, девять методов HTTP API, редактирование инженеров, очередь запусков и атомарное сохранение результатов Go-4. Общие структуры находятся в `backend/internal/contracts`.

В объединённом backend доступны storage, GeoService, PlanService и planner. `DEPENDENCY_MODE=stub` оставлен для изолированных проверок Go-2. В этом режиме координаты искусственные, а импортированные наборы получают допустимый пустой план с причиной `NOT_ASSIGNED_BY_SOLVER` и предупреждением `DEVELOPMENT_STUB`. Дорожные маршруты и оптимизация не вычисляются. Набор `contract-example` воспроизводит пример первого плана, отмену и четыре последовательных изменения статуса из контрактов. Другие события принимаются инфраструктурой, но неподдерживаемая заглушкой команда заканчивается `Run.status=failed`. Это не ограничение HTTP-интерфейса: для полного поведения нужно подключить реальный `PlanService`.

## Локальный запуск

Нужны Go 1.27 и PostgreSQL. Для локальной БД предоставлен `compose.yaml` с PostgreSQL 17. Приложение запускается из каталога `backend`. `.env` читает Docker Compose; Go-сервер получает настройки из переменных окружения.

PowerShell:

```powershell
Copy-Item .env.example .env
# При необходимости измените POSTGRES_PASSWORD в .env.
docker compose up -d --wait postgres
$env:DATABASE_URL = 'postgres://scheduler:change-me-local@localhost:5432/scheduler?sslmode=disable'
$env:DEPENDENCY_MODE = 'stub'
$env:HTTP_ADDR = '127.0.0.1:8080'
cd backend
FIXTURE_PATH=../docs/contracts/examples/backend_flow.json DATASET_DIR=../datasets/original DATABASE_URL=... SOLVER_MODE=baseline go run ./cmd/server
```

В `DATABASE_URL` укажите те же учётные данные, что использует БД. Миграции применяются при старте под транзакционной блокировкой. Повторный запуск не меняет уже применённые миграции. Пароль не записывается в журнал приложения.

| Переменная | Значение |
|---|---|
| `DATABASE_URL` | Обязательная строка подключения PostgreSQL |
| `DEPENDENCY_MODE` | Сейчас только явное `stub`; отсутствие значения останавливает сервер |
| `HTTP_ADDR` | По умолчанию `127.0.0.1:8080` |
| `DATASET_DIR` | По умолчанию `datasets/original` |
| `FIXTURE_PATH` | По умолчанию `docs/contracts/examples/backend_flow.json` |
| `TEST_DATABASE_URL` | Отдельная БД для интеграционных тестов |

На одну БД допускается один процесс сервера: он удерживает advisory lock. Сохранённые queued-запуски подбираются после перезапуска; прерванные running переходят в failed. Повтор failed-команды возвращает тот же запуск; новая попытка требует новых ключей. Планировщик вызывается вне транзакции и вне context HTTP-запроса. На одну команду установлен предел 2 минуты. Сервер корректно завершает HTTP и фонового исполнителя по сигналу остановки.

## Проверка API вручную

```powershell
$api = 'http://127.0.0.1:8080/api/v1'
Invoke-RestMethod "$api/demo-datasets"
$scenario = Invoke-RestMethod "$api/scenarios" -Method Post -ContentType 'application/json' -Body '{"demo_dataset_id":"contract-example"}'
$sid = $scenario.snapshot.scenario_id
$body = @{request_id='build-1'; snapshot_revision=1; expected_current_plan_id=$null} | ConvertTo-Json
$accepted = Invoke-RestMethod "$api/scenarios/$sid/plans" -Method Post -ContentType 'application/json' -Body $body
do {
    Start-Sleep -Milliseconds 200
    $run = Invoke-RestMethod "$api/runs/$($accepted.run_id)"
} while ($run.status -in @('queued','running'))
if ($run.status -eq 'succeeded') {
    $plan = Invoke-RestMethod "$api/plans/$($run.plan_id)"
    $plan
} else {
    $run.error
}
```

Для событий примера используйте `execution_status_flow.status_steps[].request.event` из backend JSON по порядку. В HTTP-теле передавайте только `request_id`, исходную `snapshot_revision` и `event`; URL каждого следующего события содержит ID последнего сохранённого плана. Все четыре перехода создают новую ревизию. Ветка отмены самостоятельная: начинайте с другого сценария и первого плана.

Полный HTTP-контракт: [frontend.md](contracts/frontend.md). Результаты событий сохраняются только через `CommitPlan`; отдельного endpoint подтверждения завершения нет.

## Подготовка исходных данных

Каталог содержит `east`, `southeast`, `southcentral`; их исходная дата — 2026-08-17, timezone — `Europe/Moscow`. Контрольные файлы не используются. Дополнительный `contract-example` предназначен только для разработки с заглушками, его дата — из JSON-контракта.

- CSV до 10 МБ, разделитель `;`, UTF-8 с/без BOM или Windows-1251. Принимаются предоставленные заголовки; универсальный маппинг произвольных CSV не реализован.
- Пустые строки пропускаются, строка «Адрес офиса» обрабатывается отдельно, без учёта регистра. Офис обязателен.
- Дата исходных окон должна совпадать с `date` запроса; даты молча не переносятся. Время источника московское, в API нормализуется в UTC.
- ID заявки сохраняется; ID адресов включает регион и ID заявки. `source_order` — номер исходной строки. Для исходной заявки без времени поступления используется начало местного дня.
- Ошибочная строка отражается в `issues`, не попадает в расчёт. Исходные непустые строки и версия маппинга сохраняются во внутренней таблице `imports`.
- Неизвестная пара ВК/HD не получает случайный норматив. Например, «Глобальная проблема / Информация» и «Дозаказ / Конвергенция абонента» остаются ошибками до уточнения классификации.
- Адреса сопоставляются по ID ответа геокодера. Ошибка одного адреса становится Issue; сбой всего вызова остаётся `GEO_UNAVAILABLE`.

Нормативы сверены с `docs/Нормативы.xlsx`, лист «Лист1», строки 2–5. Полная длительность включает 20 минут дороги; они вычитаются ровно один раз:

| Тип | Норматив с дорогой, мин | `service_sec` |
|---|---:|---:|
| Подключение | 90 | 4200 |
| Авария | 100 | 4800 |
| Дозаказ | 40 | 1200 |
| Ремонт | 50 | 1800 |

Модель v1 задаёт восемь отдельных инженеров на регион, смены 08:00–23:00, фиксированное сочетание навыков `connection/repair/emergency`, шесть автомобилей и двух пешеходов, четыре роутера и две приставки на инженера. Это синтетические допущения, не свойства исходных бригад. Подключение и дозаказ требуют один роутер; замена роутера или приставки — соответствующее устройство; прочие работы имеют пустую потребность. После импорта параметры инженера можно изменить PATCH до начала событий.

## Хранение и гарантии

- Снимки неизменяемы; отсутствующая точная ревизия возвращает `NOT_FOUND`.
- Build не повышает ревизию, PATCH и успешный Replan повышают её на один.
- При чтении старого снимка `current_plan_id` остаётся текущим указателем сценария.
- На регистрации команды блокируется строка сценария. Повтор определяется до проверки изменившейся версии. Тело команды хранится в JSONB; ключи request/event защищены уникальными ограничениями.
- CommitPlan повторно проверяет ревизию и текущий план. Событие, снимок, план, указатели и succeeded-запуск фиксируются одной транзакцией.
- На ошибке бизнес-данные не меняются; ошибка запуска сохраняется отдельно. Остатки оборудования и геометрия берутся из результата Go-4 без повторного вычисления.
- Build/PATCH запрещены после первого события, включая 00:00, при наличии execution или as_of после начала дня. Начальная отмена без execution не блокирует Build.

## Подключение модулей команды

В `cmd/server` заменить `testkit.Geocoder` реализацией Go-3 и `testkit.Plans` реализацией Go-4, передав последней Store как читатель снимков/планов и собственные зависимости GeoService/Planner. Затем убрать ограничение запуска только в stub-режиме и тестовый набор из конфигурации production. HTTP, исполнитель запусков и транзакции менять не требуется.

Go-4 возвращает проверенный `PlanResult` без нового ID плана и без записи в БД. Интерфейс `DataStore` принадлежит Go-2. Пример узкого читателя содержит только `GetSnapshot/GetPlan`. Владельцы Go-3/Go-4 могут использовать общие структуры и интерфейсы `backend/internal/contracts/data.go`, не создавая локальных копий.

## Тесты

```powershell
go test ./...
go vet ./...
$env:TEST_DATABASE_URL = 'postgres://scheduler:change-me-local@localhost:5432/scheduler?sslmode=disable'
go test ./...
go test -race ./...
```

Без `TEST_DATABASE_URL` тесты БД/HTTP явно пропускаются. С ним каждый тест создаёт уникальную схему и удаляет только её; нужны права CREATE SCHEMA. Проверяются реальные SQL-транзакции, миграции, параллельные повторы, две команды на одной версии, искусственный сбой в середине CommitPlan, старая история, восстановление запусков, импорт и HTTP-переходы статусов. Для `-race` требуется поддерживаемая среда с C-компилятором, например Linux-образ Go.

В тестах статусов Go-4 заменён контрактными результатами: они проверяют передачу и хранение фактов, а не подтверждают правильность ещё отсутствующей реализации Go-4. Настоящие геоданные, optimized-планировщик и сквозная демонстрация с ними остаются зависимостями соседних модулей.
