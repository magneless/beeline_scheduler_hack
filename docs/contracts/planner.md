# Планировщик — Go-1

Назначает инженеров и строит будущую часть расписания. Потребитель — Go-4. [Общие типы](common.md).

## Реализует

Go-1 реализует `Planner.Solve` и типы запроса/результата ниже. Публичный интерфейс вызывается только Go-4; HTTP и хранение в модуль не входят.

```go
type Planner interface {
    Solve(ctx context.Context, input SolveRequest) (SolveResult, error)
}
```

## Использует

Прямых вызовов чужих Go-модулей нет. Go-1 получает от Go-4 уже подготовленный `TravelMatrix`; типы матрицы определены в [geo.md](geo.md), а общие типы — в [common.md](common.md).

Семантика матрицы для реализации: `location_ids[i]` и `location_ids[j]` задают начало и конец ячейки `[i][j]`; профиль берётся по `Transport` инженера/заявки.

| Тип | Схема |
|---|---|
| `TravelMatrix` | `id`, `geo_context_id`, `location_ids: string[]`, `profiles: map[Transport][][]TravelCell` |
| `TravelCell` | `reachable: bool`, `duration_sec: int64?`, `distance_m: int64?` |

Матрица N×N использует один порядок точек во всех профилях. Достижимая ячейка содержит время и расстояние, недостижимая — `reachable=false` и оба значения `null`, диагональ — нули. Матрица должна покрывать все стартовые и заявочные точки.

Для старта используйте полный пример `solve_request`, `solve_result` и `matrix` в [examples/backend_flow.json](examples/backend_flow.json). Он содержит обязательные `mode`, `engineer_states`, `time_limit_ms`, `id` матрицы и `geo_context_id`. До подключения Go-3 матрица в примере служит тестовыми фиксированными данными; Go-4 позже подставит результат Geo без изменения алгоритма.

## Вход и выход

| Тип | Поля |
|---|---|
| `SolveRequest` | `mode: baseline \| optimized`, `orders: Order[]`, `engineers: Engineer[]`, `engineer_states: EngineerState[]`, `already_used_engineer_ids: string[]`, `travel_matrix: TravelMatrix`, `time_limit_ms: int64` |
| `SolveResult` | `routes: Route[]`, `unassigned: UnassignedOrder[]`, `termination: completed \| time_limit` |

`TravelMatrix` определён в [геоданных](geo.md). Каждый инженер имеет одно стартовое состояние. Все точки заявок и стартов присутствуют в матрице для нужного транспорта. Вход включает только доступных инженеров и оставшиеся активные заявки; уже начатые и выполненные работы в `orders` не передаются.

## Правила расчёта

- Навыки заявки входят в навыки инженера; требуемый транспорт, если указан, совпадает с его транспортом.
- Поездки и работы укладываются в смену с учётом `available_from`. Ранний приезд разрешён с ожиданием; начало работы входит в клиентское окно.
- Первая поездка начинается в `start_location_id`. Возвращение в офис не требуется.
- Недостижимые пары точек запрещены. Планировщик не обращается к внешним картам.
- `baseline`: заявки и инженеры перебираются по `source_order`, затем ID. Заявка добавляется в конец маршрута первого инженера, у которого такое добавление выполнимо. Перестановок нет.
- `optimized`: при отсутствии аварий последовательно максимизируется число назначений, минимизируется число инженеров за полный день, затем пробег. Для аварий выше этих целей ставятся число назначенных срочных заявок и раннее начало их обслуживания. Обязательные ограничения сохраняются.
- При подсчёте задействованных инженеров учитывается объединение `already_used_engineer_ids` и исполнителей нового результата.

Для приоритета срочных заявок сравнивается сначала их количество, затем сумма задержек начала относительно `window.start` во входной задаче. Go-4 ограничивает начало оставшихся окон моментом события. Это единая договорённость поиска; проверка Go-4 не требует доказательства оптимальности.

## Гарантии результата

- Каждая входная заявка встречается ровно один раз: в одном маршруте либо в `unassigned`.
- `Visit` содержит время прибытия, начала и завершения. `Leg` содержит поездку по соответствующей ячейке матрицы; геометрию добавляет Go-4 через Go-3.
- ID участков уникальны внутри результата. Go-4 сохраняет ID прошлых участков при объединении; при коллизии новые ID переименовываются согласованно с геометрией.
- `completed` означает завершение поиска, а не доказанный математический оптимум.
- При лимите времени возвращается лучший найденный допустимый результат, включая пустой план с неназначенными заявками. Некорректный вход — `INVALID_INPUT`; сбой вычислений — `COMPUTATION_FAILED`.

Коды неназначения: `NO_MATCHING_SKILL`, `NO_MATCHING_TRANSPORT`, `NO_AVAILABLE_ENGINEER`, `NO_REACHABLE_ROUTE`, `NO_FEASIBLE_SLOT`, `NOT_ASSIGNED_BY_SOLVER`. Конкретная причина используется только при подтверждении; иначе — `NOT_ASSIGNED_BY_SOLVER`.

Для самостоятельной разработки достаточно снимка с двумя инженерами, нескольких заявок и фиксированной матрицы. Получение данных, события, хранение и HTTP находятся за границей модуля.
