# Планировщик — Go-1

Назначает оставшиеся заявки инженерам и строит будущие маршруты. Вызывается Go-4. Общие типы — в [common.md](common.md).

## Реализует

```go
type Planner interface {
    Solve(ctx context.Context, input SolveRequest) (SolveResult, error)
}
```

| Тип | Поля |
|---|---|
| `SolveRequest` | `mode: baseline \| optimized \| insert_only`, `orders: Order[]`, `engineers: Engineer[]`, `engineer_states: EngineerState[]`, `already_used_engineer_ids: string[]`, `travel_matrix: TravelMatrix`, `fixed_routes: Route[]`, `protected_leg_ids: string[]`, `emergency_first?: bool`, `time_limit_ms: int64` |
| `SolveResult` | `routes: Route[]`, `unassigned: UnassignedOrder[]`, `termination: completed \| time_limit` |

## Использует

Go-1 не вызывает другие модули. Go-4 передаёт `TravelMatrix`, построенную Go-3:

| Тип | Поля |
|---|---|
| `TravelMatrix` | `id`, `geo_context_id`, `location_ids: string[]`, `profiles: map[Transport][][]TravelCell` |
| `TravelCell` | `reachable: bool`, `duration_sec: int64?`, `distance_m: int64?` |

Индексы `[i][j]` соответствуют направленному пути `location_ids[i] → location_ids[j]`; порядок точек общий для профилей, каждая матрица имеет размер N×N. Достижимая ячейка содержит время и расстояние; недостижимая имеет `reachable=false` и оба значения `null`; диагональ достижима с нулевыми значениями. Все точки стартов и заявок должны присутствовать для транспортных профилей инженеров.

## Входные данные

- `orders` содержит только ещё не начатые заявки со статусами `active`, `sent` или `en_route`. Начатые (`in_progress`), завершённые, отменённые и ранее неназначенные заявки принятого плана Go-4 сохраняет вне входа планировщика. Новая заявка, вызвавшая событие, передаётся.
- Инженеры и одноимённые `EngineerState` передаются парами. `available_from` задаёт начало доступного времени; для инженера с текущей работой и известным будущим `expected_end_at` это ожидаемое окончание, а не подтверждение фактического завершения. Если заявка `in_progress`, но `expected_end_at` отсутствует или не позже `as_of`, Go-4 не передаёт этого инженера в `Solve` и добавляет `Issue` с кодом `EXECUTION_STATE_REQUIRED`. Начатая работа сохраняется и автоматически не отменяется. Состояние также содержит стартовую точку и `equipment_available` — остаток после уже начатых работ. Резервных инженеров Go-4 передаёт только при расчёте соответствующего варианта; для них старт — офис, доступность — с момента события, запас — полный.
- `Order.work_type`: `emergency`, `connection`, `repair` или `additional`. `priority` согласуется с видом работы: обычная заявка — `normal`, авария — `urgent`. Для аварии `received_at` фиксирует фактическое поступление и ограничивает самое раннее начало обслуживания.
- Навыки обязательны: если инженеру не хватает хотя бы одного `required_skill`, назначение запрещено. Район — отдельный идентификатор сценария (`Snapshot.region_id`); его не выводят автоматически из административного поля датасета. В одном расчёте рассматриваются инженеры и заявки одного района.
- `received_at` ограничивает начало и поездки к заявке, и работы. `service_sec` — только недорожное время. Для аварии оно равно 4 800 секундам: 100-минутный норматив уже включает 20 минут первоначального резерва дороги. Фактическое время поездки из матрицы добавляется один раз, без минимального порога 1 200 секунд.
- Для каждой заявки `equipment_required` задаёт количество оборудования по типам. Назначение допустимо, только если совокупная потребность уже назначенных и новой заявок не превышает `equipment_available` инженера. Остаток учитывается после фактически начатых работ и не списывается за них повторно.
- `mode=baseline` и `mode=optimized` используют пустые `fixed_routes` и `protected_leg_ids`. `mode=insert_only` предназначен для новой обычной заявки: `fixed_routes` содержит подготовленную Go-4 будущую часть старых назначений, а `orders` — старые фиксированные визиты и одну новую заявку. Ранее неназначенные заявки остаются у Go-4 и в `Solve` не передаются.
- Каждый маршрут в `fixed_routes` фиксирует инженера, `arrival_at`, `start_at`, `end_at` и относительный порядок старых визитов. Разрешены только вставка новой заявки в свободный зазор и замена новых дорожных плеч. `protected_leg_ids` ссылаются на существующие первые участки `fixed_routes`; полностью или частично защищённый текущий `Leg` возвращается дословно, включая ID, времена и геометрию. Его остаток проверяется по сохранённому `Leg`, а не по свежей матрице. Обычная заявка не может перенаправить инженера, находящегося в пути. Времена и стартовые точки будущей части должны соответствовать `engineer_states.available_from` и состояниям инженеров.
- Суммарная потребность оборудования фиксированных визитов и новой заявки не может превышать `equipment_available`. При отсутствии допустимого зазора новая заявка возвращается с `NO_FEASIBLE_INSERTION`; если причина не доказана проверкой — с `NOT_ASSIGNED_BY_SOLVER`. Старый план остаётся стабильным. Если Go-4 обнаружил конфликт старой будущей части при проверке плана, он не вызывает `Solve`: возвращает `Issue` с кодом `EXISTING_PLAN_CONFLICT`, предупреждение и новую заявку в `unassigned` с `reason_code=NOT_ASSIGNED_BY_SOLVER` и объяснением конфликта. `EXISTING_PLAN_CONFLICT` не является `reason_code`. После принятия плана неназначенная обычная заявка сохраняется для разбора вне сервиса и автоматически не участвует в следующих расчётах.
- Для аварии приоритет не прерывает уже начатую работу: она завершается, после чего подходящая бригада может получить аварию и оставшийся маршрут может быть перестроен. `emergency_first=true` заставляет вариант с допуском опоздания сначала распределить аварии. Ориентир реакции на сетевую аварию — 1–2 часа; это не жёсткий SLA и не новое поле контракта. Новая обычная заявка в сохранённом алгоритме вставляется в свободный интервал; диспетчерский выбор вариантов описан в [plans.md](plans.md).
- Заправка и очереди на АЗС находятся вне задачи. Жёсткая грузоподъёмность для пешего или велосипедного инженера не обязательна; 1–2 единицы оборудования в рюкзаке — лишь модельное допущение. Для заявки без оборудования допускается `equipment_required={}`.
- При `time_limit` в `insert_only` возвращается fallback из `fixed_routes` и новая заявка в `unassigned`; пустой план недопустим, старые фиксированные визиты нельзя переносить в `unassigned`. Временные окна фиксированы в базовом сценарии; эксперименты с более гибкими окнами допустимы как отдельная модельная проверка и не меняют этот контракт. Один CSV-файл считается одним регионом; заявки Москвы и удалённых городов внутри него относятся к одному сценарию. Пересечение территорий допустимо, но лишние перегоны между ними следует минимизировать.

## Ограничения расчёта

- Поездка и работа начинаются не раньше `received_at`; работа дополнительно начинается не раньше начала клиентского окна. Требуемый транспорт, если указан, должен совпадать с транспортом инженера. Прибытие раньше окна допустимо с ожиданием; начало должно входить в клиентское окно, завершение — не позже конца смены. Дорога берётся из соответствующей ячейки матрицы; недостижимые пары не используются. Возвращение в офис не требуется.
- Цель `optimized` — зафиксированная модель решения по иерархии QA: лексикографически максимизировать число назначенных аварий, затем подключений, затем ремонтов и дозаказов вместе; минимизировать сумму задержек начала аварий `start_at − max(window.start, received_at)`; минимизировать число задействованных инженеров; минимизировать общий пробег. Число инженеров считается по объединению `already_used_engineer_ids` и новых исполнителей. При полном равенстве сравнивается список назначений в порядке `source_order`, ID заявки; для каждой заявки — ID инженера, позиция и время начала. QA задаёт иерархию типов работ и приоритет метрик, а эту точную формулу выбирает решение.
- `baseline` — исходный жадный вариант: заявки и инженеры перебираются по `source_order`, затем ID; приоритетная сортировка не применяется. Заявка добавляется в конец маршрута первого допустимого инженера, перестановок нет.
- Заявка, для которой допустимого назначения нет, возвращается в `unassigned` с причиной. Планировщик не отбрасывает заявки молча.

Пример аварийного визита: сумма недорожного времени работы и дороги, без ожидания окна, равна `80 + 5 = 85` минут при поездке 5 минут и `80 + 30 = 110` минут при поездке 30 минут. Это нормативная длительность, не обещание времени окончания от поступления и не жёсткий дедлайн. Пример оборудования: при остатке `{router: 1}` две заявки, каждая требующая один роутер, нельзя назначить одному инженеру в одном плане.

## Результат и ошибки

- Каждая входная заявка встречается ровно один раз: в маршруте либо в `unassigned`. `Visit` содержит прибытие, начало и конец; `Leg` строится по соответствующей ячейке матрицы. ID участков уникальны внутри результата; геометрию Go-4 добавляет через Go-3.
- `completed` означает окончание поиска, не доказательство математического оптимума. При `time_limit` возвращается лучший допустимый результат; для `insert_only` обязательно возвращаются `fixed_routes` и новая заявка в `unassigned`, пустой план недопустим.
- Коды неназначения: `NO_MATCHING_SKILL`, `NO_MATCHING_TRANSPORT`, `NO_MATCHING_EQUIPMENT`, `NO_AVAILABLE_ENGINEER`, `NO_REACHABLE_ROUTE`, `NO_FEASIBLE_SLOT`, `NO_FEASIBLE_INSERTION`, `NOT_ASSIGNED_BY_SOLVER`. Указывать конкретную причину можно только если она подтверждена проверкой; иначе используется `NOT_ASSIGNED_BY_SOLVER`. Некорректный вход — `INVALID_INPUT`, сбой вычисления — `COMPUTATION_FAILED`.

Для локальной разработки достаточно тестовых инженеров, заявок и фиксированной матрицы из [примера backend](examples/backend_flow.json). Расчёты и эксперименты выполняются только на синтетических данных; контрольные файлы не используются. Импорт, хранение, события и HTTP находятся за границей модуля.
