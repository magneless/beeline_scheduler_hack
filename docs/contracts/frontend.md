# HTTP API — Go-2 и Frontend

Префикс `/api/v1`, JSON — `snake_case`, типы и единицы — из [общих контрактов](common.md). Go-2 реализует API, Frontend использует его и согласованные mock-ответы.

## Что реализует Frontend

- экран сценария: выбор набора, импорт CSV, дата и регион;
- редактирование инженера до начала операционного дня: навыки, транспорт, смена, доступность и запас оборудования (`router`, `tv_box`);
- рабочее пространство диспетчера: карта маршрутов, расписание, карточки заявок, показатели и остаток оборудования по бригадам;
- запуск расчёта и опрос состояния запуска;
- отображение неназначенных заявок, ошибок исходных данных и изменений после события;
- подтверждение статусов заявки диспетчером: «Отправлено», «В пути», «Выполняется», «Завершено», «Отменена»;
- перепланирование по новой заявке, смене её статуса, отмене заявки или недоступности инженера;
- предупреждение о незаданном или просроченном ожидаемом окончании текущей работы;
- обработка ошибок API и устаревшей ревизии с предложением перечитать сценарий.

Frontend не рассчитывает маршруты, назначения, времена, расстояния или метрики. Он отображает значения из ответов Go-2 и передаёт `expected_revision`, `snapshot_revision` и `expected_current_plan_id` без изменения.

## Что Frontend использует от Go-2

Go-2 предоставляет HTTP API ниже, хранение сценариев, снимков, планов и запусков. Frontend должен реализовать клиент этих методов и типы ответов по [общим контрактам](common.md): `ScenarioView`, `Snapshot`, `Order`, `OrderExecution`, `WorkType`, `Equipment`, `Engineer`, `Run`, `Plan` (включая `equipment_remaining: map[engineer_id]map[Equipment]int64`), `Issue`, `Route`, `Visit`, `Leg`, `UnassignedOrder`, `Metrics`, `PlanChange`, `Event`.

## Методы

| Метод и путь | Вход | Успешный ответ |
|---|---|---|
| `GET /demo-datasets` | — | `200 {items: [{id, name, region_id, date, timezone}]}` |
| `POST /scenarios` | `{demo_dataset_id}` | `201 ScenarioView` |
| `POST /scenarios/import` | multipart: `file` — CSV, `region_id`, `date` | `201 ScenarioView`, включая ошибки отдельных строк |
| `GET /scenarios/{id}` | Необязательный `revision` в query; без него — текущая | `200 ScenarioView` |
| `PATCH /scenarios/{id}/engineers/{engineer_id}` | `{expected_revision, skills?, transport?, shift?, available?, equipment_stock?}` | `200 ScenarioView` с новой ревизией; при блокирующем состоянии — `409 EVENT_CONFLICT` |
| `POST /scenarios/{id}/plans` | `{request_id, snapshot_revision, expected_current_plan_id}` | `202 {run_id}`, если состояние не блокирует Build |
| `POST /plans/{id}/events` | `{request_id, snapshot_revision, event}`; ревизия до события | `202 {run_id}`; событие, новая ревизия и план применяются атомарно |
| `GET /runs/{id}` | — | `200 Run` |
| `GET /plans/{id}` | — | `200 Plan` |

`scenario_id` обычного расчёта берётся из URL. Для события Go-2 получает сценарий по плану из URL; этот ID становится `base_plan_id`. Формат `event` — в [common.md](common.md), семантика — в [plans.md](plans.md). Приоритет типа работ фиксирован: авария → подключение → ремонт/дозаказ.

Обычная новая заявка передаётся как `ordinary_order_added` с полями `order`, `location?`; внутри `order.work_type` — `connection|repair|additional`, `priority=normal`, `status=active`, `execution=null`, `received_at=occurred_at`. Полная схема события — в [common.md](common.md). Интерфейс показывает, назначена заявка или неназначена: при отсутствии свободной щели — `NO_FEASIBLE_INSERTION`, а при конфликте устаревшего плана — Issue `EXISTING_PLAN_CONFLICT` и `UnassignedOrder.reason_code=NOT_ASSIGNED_BY_SOLVER`; это не HTTP-ошибка.

### Подтверждение статуса заявки

| Статус | Короткая подпись в интерфейсе | Действие диспетчера |
|---|---|---|
| `active` | Активна | Заявка ещё не отправлена; наличие назначения показывается отдельно |
| `sent` | Отправлено | Подтвердить передачу заявки бригаде |
| `en_route` | В пути | Подтвердить выезд; `occurred_at` — фактическое время выезда |
| `in_progress` | Выполняется | Подтвердить начало работ и при наличии указать ожидаемое окончание |
| `completed` | Завершено | Подтвердить завершение по информации бригады |
| `cancelled` | Отменена | Указать причину отмены |

Допустимая последовательность: `active → sent → en_route → in_progress → completed`; `sent → in_progress` разрешён, если инженер уже находится по адресу заявки и отдельная поездка не нужна. Frontend отправляет `order_status_changed` через тот же `POST /plans/{id}/events` с `order_id`, целевым статусом, `engineer_id` и фактическим `occurred_at`. При `in_progress` `expected_end_at` опционален, но если указан — позже времени события; диспетчер может обновить оценку повторным событием. Если время отсутствует или уже прошло, интерфейс показывает предупреждение «Уточните время завершения» (`EXECUTION_STATE_REQUIRED`); система сохраняет текущую работу и не выдаёт этой бригаде будущие заявки до уточнения. Другие бригады продолжают перепланирование.

«Завершить» фиксирует факт только по подтверждению диспетчера, не по времени плана. «Отменить» требует выбрать причину `client_refusal` («Отказ клиента») или `cannot_perform` («Невозможно выполнить»); отмена допустима и для начатой заявки, но завершённую или уже отменённую отменить нельзя. Если будущая заявка в `sent`/`en_route` переназначается другой бригаде, её статус сбрасывается в `active` и требуется новая отправка; прошлые поездки остаются в истории. `in_progress` не сбрасывается при переназначении. Закрытые заявки видны отдельно от назначений и не включаются в дальнейшее перепланирование. Порядок типов: авария → подключение → ремонт/дозаказ.

В `PATCH` отсутствие поля означает «не менять»; `null` для изменяемых полей запрещён. `skills=[]` допустим и означает отсутствие навыков. `equipment_stock` — карта количеств по `router` и `tv_box`. `expected_current_plan_id=null` означает отсутствие текущего плана.

Build и PATCH доступны, пока нет блокирующего состояния: текущий план не создан событием (`base_plan_id=null`), у всех заявок `execution=null`, а `as_of` не позже начала местного дня. Первое событие, включая событие ровно в 00:00, блокирует повторный Build и ручное редактирование инженеров. Начальная отменённая заявка без `execution` не блокирует первый Build. После блокировки Frontend отправляет изменения через события и `Replan`. Для показа фактического времени используется `timezone` региона: исходные времена московские, а `region_id` — отдельный район/сценарий, не административное поле датасета. Все эксперименты выполняются только на синтетических наборах. Внешняя интеграция с системами диспетчеризации не требуется.

## Импорт

Первая версия принимает CSV с заголовками предоставленных наборов: заявка, типы работ, начало/окончание, адрес и остальные исходные поля. Идентификация варианта, сопоставление типов с навыками и нормативами принадлежат Go-2; выбранный маппинг хранится вместе с подготовленным набором. Универсальное сопоставление произвольных CSV через интерфейс не входит в контракт.

Инженеры и нормативы при импорте подставляются из подготовленного набора региона; затем инженеры редактируются через API. `region_id` выбирается из регионов, возвращённых `/demo-datasets`. Время файлов интерпретируется по правилам исходного набора и нормализуется backend.

## Получение плана

1. Отправить команду расчёта и получить `run_id`.
2. Опросить `GET /runs/{id}` до `succeeded` или `failed`.
3. При успехе получить `plan_id`, затем загрузить `Plan` и его `Snapshot` по точной `snapshot_revision`.

`Run = {id, scenario_id, status, plan_id, error}`. До успеха `plan_id=null`; при отсутствии ошибки `error=null`. Статусы: `queued`, `running`, `succeeded`, `failed`.

`Plan` содержит маршруты с геометрией, неназначенные заявки, фактически завершённые (`completed_order_ids`), отменённые заявки, ошибки и предупреждения данных, метрики (в том числе `completed_count`), необязательные метрики базового алгоритма и список изменений. Для сравнения при перепланировании предыдущий план загружается по `base_plan_id`. `EXECUTION_STATE_REQUIRED` в этом сценарии — `Issue` плана, а не HTTP-ошибка: бригада сохраняет текущую работу, будущие назначения для неё не строятся до подтверждения/актуальной оценки времени окончания.

Данные карточек, настройки инженеров и начальная выдача оборудования берутся из снимка соответствующего плана. До первого Build показывается `Engineer.equipment_stock`; после расчёта для остатка используется только `Plan.equipment_remaining`, которое backend возвращает по всем инженерам. Frontend не вычисляет расход и не вычитает будущие резервы. Текущие отредактированные данные нельзя молча показывать как вход старой версии. Километры, минуты и местное время — форматирование интерфейса; назначения и метрики рассчитывает backend.

## Ошибки и повторы

Ошибки HTTP возвращаются в едином формате:

```json
{
  "code": "STALE_VERSION",
  "message": "Исходные данные или текущий план изменились",
  "details": {}
}
```

| HTTP | Коды |
|---|---|
| `400` | Нечитаемый JSON/CSV или некорректный multipart: `INVALID_INPUT` |
| `404` | `NOT_FOUND` |
| `409` | `STALE_VERSION`, `EVENT_CONFLICT`, `IDEMPOTENCY_CONFLICT` |
| `422` | Корректный по формату запрос с недопустимыми значениями: `INVALID_INPUT` |
| `503` | `GEO_UNAVAILABLE` |
| `500` | `INVALID_PLAN`, `COMPUTATION_FAILED` |

После ответа `202` ошибки расчёта приходят в `Run.error` при `status=failed`, а чтение запуска возвращает `200`. Повтор той же команды с тем же ключом возвращает тот же `run_id`, включая завершённый запуск; конфликт содержимого возвращает `409`.

## Начало самостоятельной разработки

Готовые mock-ответы находятся в [frontend_flow.json](examples/frontend_flow.json), привязка ключей к HTTP-методам — в [examples/README.md](examples/README.md). Основная ветка: загрузка сценария, запуск, готовый план и отмена будущей заявки. Отдельные ветки показывают подтверждение статусов до завершения и поступление аварии при ограниченном оборудовании; также приведены ошибка строки импорта и конфликт версии.

Сначала реализовать HTTP-клиент и экраны на этих ответах, затем заменить mock API на сервер Go-2 с теми же методами. `snapshot_revision` плана совпадает с ревизией его снимка; старый план отображается по старому снимку. Время API форматируется в местной зоне региона. Интерфейс предназначен диспетчеру; отдельный экран/клиент инженера не входит в требования.
