# HTTP API — Go-2 и Frontend

Префикс `/api/v1`, JSON — `snake_case`, типы и единицы — из [общих контрактов](common.md). Go-2 реализует API, Frontend использует его и согласованные mock-ответы.

## Что реализует Frontend

- экран сценария: выбор набора, импорт CSV, дата и регион;
- редактирование инженера до начала операционного дня: навыки, транспорт, доступность, резерв и запас оборудования (`router`, `tv_box`); обязательная смена 10:00–22:00 отображается без редактирования;
- рабочее пространство диспетчера: карта маршрутов, расписание, карточки заявок, показатели и остаток оборудования по бригадам;
- запуск расчёта вариантов на одинаковых данных, сравнение на карте и в расписании, выбор рабочего плана;
- отображение неназначенных заявок, ошибок исходных данных и изменений после события;
- фиксация начала и завершения работы диспетчером; состояние «В пути» определяется по времени выезда в плане;
- варианты перепланирования при аварии, обычной заявке, отмене и недоступности инженера, включая допуск опоздания и привлечение резерва;
- предупреждение о работе, плановое время которой истекло, с ожиданием фактического завершения;
- обработка ошибок API и устаревшей ревизии с предложением перечитать сценарий.

Frontend не рассчитывает маршруты, назначения, времена, расстояния или метрики. Он отображает значения из ответов Go-2 и передаёт `expected_revision`, `snapshot_revision` и `expected_current_plan_id` без изменения.

По [QA из чата 4 и уточнению команды](../qa_chat_4/QA_processed.md) график бригад фиксирован: **10:00–22:00** в часовом поясе сценария. Поле `shift` в API сохраняется, но произвольные значения не допускаются; при передаче иного интервала контракт требует `422 INVALID_INPUT`. Выбор недоступности инженера не меняет границы смены.

В карточке работы диспетчер вводит время начала или фактического завершения. Прогноз окончания при начале заполняется автоматически по нормативной длительности; ручного поля и кнопки обновления оценки нет. Ввод времени имеет точность до минуты: если выбрана показанная минута планового начала или окончания, сохраняются секунды соответствующей границы визита. Время не сдвигается назад; предыдущая минута остаётся более ранним событием. Следующая работа доступна только после закрытия предыдущих заявок бригады; интерфейс показывает препятствующую заявку и переход к ней, backend проверяет то же условие.

## Что Frontend использует от Go-2

Go-2 предоставляет HTTP API ниже, хранение сценариев, снимков, планов и запусков. Frontend должен реализовать клиент этих методов и типы ответов по [общим контрактам](common.md): `ScenarioView`, `Snapshot`, `Order`, `OrderExecution`, `WorkType`, `Equipment`, `Engineer`, `Run`, `Plan` (включая `equipment_remaining: map[engineer_id]map[Equipment]int64`), `Issue`, `Route`, `Visit`, `Leg`, `UnassignedOrder`, `Metrics`, `PlanChange`, `Event`.

## Методы

| Метод и путь | Вход | Успешный ответ |
|---|---|---|
| `GET /demo-datasets` | — | `200 {items: [{id, name, region_id, date, timezone}]}` |
| `POST /scenarios` | `{demo_dataset_id}` | `201 ScenarioView` |
| `POST /scenarios/import` | multipart: `file` — CSV заявок, `engineers_file` — CSV бригад, `date`, `office_address?`, `office_point?` — JSON `{lat, lon}`; `region_id?` для прежнего импорта | `201 ScenarioView`, включая ошибки отдельных строк |
| `GET /scenarios/{id}` | Необязательный `revision` в query; без него — текущая | `200 ScenarioView` |
| `GET /scenarios` | — | `200 {items: ScenarioSummary[]}` — сохранённые дни, по дате от новых к старым; поля: `scenario_id`, `revision`, `region_id`, `date`, `order_count`, `unlocated_count`, `current_plan_id` |
| `PATCH /scenarios/{id}/engineers/{engineer_id}` | `{expected_revision, skills?, transport?, shift?, available?, equipment_stock?}` | `200 ScenarioView` с новой ревизией; при блокирующем состоянии — `409 EVENT_CONFLICT` |
| `POST /scenarios/{id}/proposals` | `{request_id, snapshot_revision, expected_current_plan_id, solve_mode?, event?}` | `201 Proposal` с рассчитанными вариантами; повтор того же запроса — `200 Proposal` |
| `GET /scenarios/{id}/proposals/current` | — | `200 Proposal` для актуального непринятого набора либо `null` |
| `POST /proposals/{id}/accept` | `{request_id, option_key}` | `200 Plan`; сохраняет выбранный результат, событие и новую ревизию атомарно |
| `POST /scenarios/{id}/plans` | `{request_id, snapshot_revision, expected_current_plan_id}` | `202 {run_id}`, если состояние не блокирует Build |
| `POST /plans/{id}/events` | `{request_id, snapshot_revision, event}`; ревизия до события | `202 {run_id}`; событие, новая ревизия и план применяются атомарно |
| `GET /runs/{id}` | — | `200 Run` |
| `GET /plans/{id}` | — | `200 Plan` |

`scenario_id` обычного расчёта берётся из URL. Для события Go-2 получает сценарий по плану из URL; этот ID становится `base_plan_id`. Формат `event` — в [common.md](common.md), семантика — в [plans.md](plans.md). Приоритет типа работ фиксирован: авария → подключение → ремонт/дозаказ.

`Proposal = {id, scenario_id, request_id, snapshot_revision, expected_current_plan_id, solve_mode?, event?, options: PlanOption[]}`. Вариант содержит `key`, `label`, вычисленный `result` с полными маршрутом, снимком и метриками, `lateness`, `reserve_engineer_ids` и при совпадении `identical_to`. При первом расчёте доступны `strict` и `late_emergency`; при аварии — `strict`, `late_emergency`, `reserve`; при остальных событиях — `strict`, `reserve` и отдельное действие `original` для сохранения прежнего расписания по правилам [перерасчёта](../route-recalculation.md). Диспетчер принимает один вариант; только тогда он становится рабочим планом. Интерфейс показывает исходное окно аварии, плановое прибытие, опоздание, изменённые назначения, неназначенные заявки с причинами, состав инженеров и пробег. `GET .../current` позволяет восстановить незавершённое сравнение после обновления страницы.

Обычная новая заявка передаётся как `ordinary_order_added` с полями `order`, `location?`; внутри `order.work_type` — `connection|repair|additional`, `priority=normal`, `status=active`, `execution=null`, `received_at=occurred_at`. Полная схема события — в [common.md](common.md). Интерфейс показывает, назначена заявка или неназначена: при отсутствии свободной щели — `NO_FEASIBLE_INSERTION`, а при конфликте устаревшего плана — Issue `EXISTING_PLAN_CONFLICT` и `UnassignedOrder.reason_code=NOT_ASSIGNED_BY_SOLVER`; это не HTTP-ошибка.

### Подтверждение статуса заявки

| Статус | Короткая подпись в интерфейсе | Действие диспетчера |
|---|---|---|
| `active` | Активна | Работа ещё не начата; наличие назначения показывается отдельно |
| `sent` | Отправлено | Исторический статус передачи заявки |
| `en_route` | В пути | Показать состояние по времени выезда действующего плана |
| `in_progress` | Выполняется | Подтвердить начало работ и при наличии указать ожидаемое окончание |
| `completed` | Завершено | Подтвердить завершение по информации бригады |
| `cancelled` | Отменена | Указать причину отмены |

Состояние `en_route` следует из времени выезда в действующем плане. Frontend отправляет `order_status_changed` только для начала и завершения через `POST /plans/{id}/events` с `order_id`, целевым статусом (`in_progress` или `completed`), `engineer_id` и фактическим `occurred_at`. При `in_progress` `expected_end_at` опционален, но если указан — позже времени события; диспетчер может обновить оценку повторным событием. Если время отсутствует или уже прошло, интерфейс показывает предупреждение «Уточните время завершения» (`EXECUTION_STATE_REQUIRED`); система сохраняет текущую работу и не выдаёт этой бригаде будущие заявки до уточнения. Другие бригады продолжают перепланирование.

«Завершить» фиксирует факт только по подтверждению диспетчера, не по времени плана. «Отменить» требует выбрать причину `client_refusal` («Отказ клиента») или `cannot_perform` («Невозможно выполнить»); отмена допустима до начала работы, включая путь; начатую, завершённую и уже отменённую отменить нельзя. Если будущая заявка в `sent`/`en_route` переназначается другой бригаде, её статус сбрасывается в `active`; передачу нового маршрута бригаде диспетчер выполняет вне приложения. Прошлые поездки остаются в истории. Начатая работа не прерывается и не переназначается. Закрытые заявки видны отдельно от назначений и не включаются в дальнейшее перепланирование. Порядок типов: авария → подключение → ремонт/дозаказ.

В `PATCH` отсутствие поля означает «не менять»; `null` для изменяемых полей запрещён. `skills=[]` допустим и означает отсутствие навыков. `equipment_stock` — карта количеств по `router` и `tv_box`. `expected_current_plan_id=null` означает отсутствие текущего плана.

Build и PATCH доступны, пока нет блокирующего состояния: текущий план не создан событием (`base_plan_id=null`), у всех заявок `execution=null`, а `as_of` не позже начала местного дня. Первое событие, включая событие ровно в 00:00, блокирует повторный Build и ручное редактирование инженеров. Начальная отменённая заявка без `execution` не блокирует первый Build. После блокировки Frontend отправляет изменения через события и `Replan`. Для показа фактического времени используется `timezone` региона: исходные времена московские, а `region_id` — отдельный район/сценарий, не административное поле датасета. Все эксперименты выполняются только на синтетических наборах. Внешняя интеграция с системами диспетчеризации не требуется.

## Импорт

Первая версия принимает CSV с заголовками предоставленных наборов: заявка, типы работ, начало/окончание, адрес и остальные исходные поля. Идентификация варианта, сопоставление типов с навыками и нормативами принадлежат Go-2; выбранный маппинг хранится вместе с подготовленным набором. Универсальное сопоставление произвольных CSV через интерфейс не входит в контракт.

На экране подготовки дня заявки и бригады загружаются одним multipart-запросом. Без `region_id` создаётся рабочий день с техническим идентификатором `custom` и часовым поясом `Europe/Moscow`; файл бригад обязателен. Состав проверяется до геокодирования, сценарий сохраняется только после проверки обоих файлов. Офис можно передать адресом и подтверждённой точкой; иначе используется строка офиса из CSV. Выбранный офис имеет приоритет над строкой файла. Каждый CSV ограничен 10 МБ. Дата должна совпадать с окнами заявок. Демонстрационные инженеры при таком импорте не создаются.

Прежний импорт с `region_id` поддерживает отдельную загрузку бригад через `/scenarios/{id}/engineers/import`. Готовые наборы из `/demo-datasets` открываются с демонстрационным составом; служебные контрактные примеры в каталог интерфейса не входят.

Меню «Районы» использует `GET /scenarios` и открывает сохранённый день по `scenario_id`, без создания сценария и повторного геокодирования. В список входят и дни с неуточнёнными адресами; `order_count` включает такие заявки. Несколько сохранённых дней с одинаковыми районом и датой остаются отдельными пунктами.

## Получение плана

1. Отправить `POST /scenarios/{id}/proposals` с текущими `snapshot_revision`, `expected_current_plan_id`, новым `request_id` и при событии — `event`.
2. Сравнить `options` ответа на карте и в расписании. После обновления страницы получить актуальный набор через `GET /scenarios/{id}/proposals/current`.
3. Отправить `POST /proposals/{id}/accept` с новым `request_id` и выбранным `option_key`, затем загрузить сохранённый `Plan` и его точный снимок.

Для отображения хода расчёта `POST /scenarios/{id}/proposals` и `POST /scenarios/{id}/plans/compare` принимают `Accept: text/event-stream`. В этом режиме сервер передаёт события SSE: `progress` с `{stage, message, completed, total, variant_label?}`, `heartbeat` для проверки связи, затем `result` с обычным JSON-результатом либо `error` с ошибкой контракта. `completed` и `total` означают число готовых и общее число вариантов, а не оценку оставшегося времени. Без этого заголовка сохраняется обычный JSON-ответ. Ошибки проверки запроса до открытия потока также возвращаются обычным HTTP-ответом.

Создание сценария (`POST /scenarios`) и импорт CSV (`POST /scenarios/import`, multipart) поддерживают тот же поток. Этапы: `preparing`, `reading`, `office` (для CSV), `geocoding`, `geocoding_complete`, `saving`. Здесь `completed` и `total` считают обработанные адреса заявок, включая адреса, требующие уточнения. При `total: 0` показывается неопределённый индикатор; завершение обработки адресов ещё не означает сохранение сценария — переход на карту выполняется после `result`. Поток возвращает HTTP 200, обычный JSON при успешном создании сохраняет HTTP 201.

Индикатор показывает этап, число готовых вариантов и прошедшее время. Если сигналы от сервера перестают приходить, интерфейс сообщает о задержке связи. Для команд с опросом `Run` используется индикатор без процентов: API этих команд сообщает только очередь и выполнение. Карта остаётся доступной во время расчёта.

Прямые endpoints `/scenarios/{id}/plans` и `/plans/{id}/events` возвращают `Run = {id, scenario_id, status, plan_id, error}` со статусами `queued`, `running`, `succeeded`, `failed`; они оставлены для прямых вызовов и подтверждения начала/завершения работы. Отмена заявки из `plan.unassigned` также отправляется в `/plans/{id}/events`: без расчёта вариантов, с индикатором «Отмена заявки» и результатом «Заявка отменена». Backend проверяет, что заявка действительно неназначена; отмена назначенной заявки требует `Proposal`. В пользовательском выборе вариантов применяется `Proposal`.

Для групповой отмены то же событие `order_cancelled` принимает `payload: {order_ids: ["id-1", "id-2"], reason: "cannot_perform"}` вместо одиночного `order_id`. Список непустой, без повторов, все заявки находятся в `plan.unassigned`. Время и причина общие. Один `Run`, одно событие и одна новая ревизия сохраняют весь пакет атомарно; устаревший план или недопустимая заявка отклоняют всю операцию. Повтор с теми же ключами идемпотентен, порядок ID не влияет. Чекбоксы доступны у неназначенных заявок с определённым адресом; «Выбрать все» учитывает поиск и фильтры. При изменении поиска, фильтра или сценария выбор очищается.

`Plan` содержит маршруты с геометрией, неназначенные заявки, фактически завершённые (`completed_order_ids`), отменённые заявки, ошибки и предупреждения данных, метрики (в том числе `completed_count`), необязательные метрики базового алгоритма и список изменений. Для сравнения при перепланировании предыдущий план загружается по `base_plan_id`. `EXECUTION_STATE_REQUIRED` в этом сценарии — `Issue` плана, а не HTTP-ошибка: бригада сохраняет текущую работу, будущие назначения для неё не строятся до подтверждения/актуальной оценки времени окончания.

Данные карточек, настройки инженеров и начальная выдача оборудования берутся из снимка соответствующего плана. До первого Build показывается `Engineer.equipment_stock`; после расчёта для остатка используется только `Plan.equipment_remaining`, которое backend возвращает по всем инженерам. Frontend не вычисляет расход и не вычитает будущие резервы. Текущие отредактированные данные нельзя молча показывать как вход старой версии. Километры, минуты и местное время — форматирование интерфейса; назначения и метрики рассчитывает backend.

## Ошибки и повторы

Ошибки HTTP возвращаются в едином формате:

```json
{
  "code": "STALE_VERSION",
  "message": "Исходные данные или текущий план изменились",
  "details": {}
}
```

| HTTP | Коды |
|---|---|
| `400` | Нечитаемый JSON/CSV или некорректный multipart: `INVALID_INPUT` |
| `404` | `NOT_FOUND` |
| `409` | `STALE_VERSION`, `EVENT_CONFLICT`, `IDEMPOTENCY_CONFLICT` |
| `422` | Корректный по формату запрос с недопустимыми значениями: `INVALID_INPUT` |
| `503` | `GEO_UNAVAILABLE` |
| `500` | `INVALID_PLAN`, `COMPUTATION_FAILED` |

Для прямого запуска после ответа `202` ошибки расчёта приходят в `Run.error` при `status=failed`, а чтение запуска возвращает `200`. Повтор предложения с тем же `request_id` и содержимым возвращает тот же набор; повтор принятия с тем же `request_id` и вариантом — тот же план. Конфликт содержимого возвращает `409`.

## Начало самостоятельной разработки

Готовые mock-ответы находятся в [frontend_flow.json](examples/frontend_flow.json), привязка ключей к HTTP-методам — в [examples/README.md](examples/README.md). Основная ветка: загрузка сценария, запуск, готовый план и отмена будущей заявки. Отдельные ветки показывают подтверждение статусов до завершения и поступление аварии при ограниченном оборудовании; также приведены ошибка строки импорта и конфликт версии.

Сначала реализовать HTTP-клиент и экраны на этих ответах, затем заменить mock API на сервер Go-2 с теми же методами. `snapshot_revision` плана совпадает с ревизией его снимка; старый план отображается по старому снимку. Время API форматируется в местной зоне региона. Интерфейс предназначен диспетчеру; отдельный экран/клиент инженера не входит в требования.

Кнопка «Собрать с нуля» открывает независимое сравнение базового и оптимизированного маршрутов на исходных данных первой версии плана. В окне можно переключать алгоритм и выделять маршрут бригады; рабочий план и фактические статусы не меняются.
