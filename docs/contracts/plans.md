# Управление планами и перепланирование — Go-4

Управляет последовательностью расчёта и проверяет результат. Вызывается Go-2; использует `DataStore`, `GeoService` и `Planner`. [Общие типы](common.md).

`Build` и `Replan` входят в основу. Go-4 отделяет подтверждённое выполнение от прогнозного расписания, учитывает остатки оборудования и передаёт Go-1 приоритеты из [спецификации с QA](../specification.md). Никакое сравнение с плановым временем само по себе не закрывает заявку.

## Реализует

`PlanService` вызывается инфраструктурой Go-2.

```go
type PlanService interface {
    Build(ctx context.Context, input BuildPlanRequest) (PlanResult, error)
    Replan(ctx context.Context, input ReplanRequest) (PlanResult, error)
}
```

## Использует от других разработчиков

Все три зависимости передаются при создании модуля. Ниже — сигнатуры, по которым можно написать заглушки, не ожидая реализации соседей.

### Go-2: чтение снимка и плана

```go
// Потребительская часть DataStore: запись Go-4 не нужна.
type PlanDataReader interface {
    GetSnapshot(ctx context.Context, scenarioID string, revision int64) (Snapshot, error)
    GetPlan(ctx context.Context, planID string) (Plan, error)
}
```

`GetSnapshot` возвращает **точную** неизменяемую ревизию. `GetPlan` возвращает сохранённый план с геометрией, метриками и ссылкой на ревизию. Отсутствующий объект — `NOT_FOUND`; актуальная ревизия не подставляется вместо запрошенной. `Snapshot`, `Plan` и вложенные типы — в [common.md](common.md). Полный контракт владельца: [data.md](data.md).

`CommitPlan` принадлежит Go-2 и вызывается им после возврата из `PlanService`. Go-4 не вызывает запись, HTTP API или управление `Run`.

### Go-3: дорожные расчёты

```go
type GeoService interface {
    Geocode(ctx context.Context, input GeocodeRequest) (GeocodeResult, error)
    BuildMatrix(ctx context.Context, input MatrixRequest) (TravelMatrix, error)
    BuildRoutes(ctx context.Context, input RoutesRequest) (RoutesGeometry, error)
    PositionAt(ctx context.Context, input PositionRequest) (PositionResult, error)
}
```

| Метод | Что передаёт Go-4 | Что использует из ответа |
|---|---|---|
| `Geocode` | `{region_id, locations: LocationInput[]}` — новый адрес срочной заявки | `items: [{location_id, location: Location?, issue: Issue?}]` |
| `BuildMatrix` | `{locations: Location[], profiles: Transport[], geo_context_id: string?}` — заявки и новые стартовые точки | `TravelMatrix = {id, geo_context_id, location_ids: string[], profiles: map[Transport][][]TravelCell}` |
| `BuildRoutes` | `{geo_context_id, locations: Location[], legs: [{leg_id, from_location_id, to_location_id, profile}]}` — выбранные планировщиком участки | `items: [{leg_id, geometry: Point[]}]`, сопоставление по `leg_id` |
| `PositionAt` | `{leg: Leg, at}` — сохранённый участок с геометрией и время события | `{point: Point, elapsed_duration_sec, elapsed_distance_m, elapsed_geometry: Point[]}` |

`TravelCell = {reachable: bool, duration_sec: int64?, distance_m: int64?}`. Индексы `[i][j]` соответствуют `location_ids[i] → location_ids[j]`, все профили используют одинаковый порядок; недостижимые пары имеют `null` вместо времени и расстояния. Матрица может быть несимметричной.

Для обычного расчёта `geo_context_id=null` позволяет Go-3 выбрать контекст. При перепланировании используется контекст участков базового плана; если участков нет, допустим `null`. Геометрию новых участков строят в контексте использованной матрицы. `PositionAt` воспроизводит положение по сохранённому участку.

Ошибки зависимости: `INVALID_INPUT` и `GEO_UNAVAILABLE`; ошибки отдельных адресов передаются в `items[].issue`. Отсутствие геометрии хотя бы одного участка означает ошибку всего `BuildRoutes`. При ошибке текущий план не заменяется. Полная семантика: [geo.md](geo.md).

### Go-1: расчёт назначений

```go
type Planner interface {
    Solve(ctx context.Context, input SolveRequest) (SolveResult, error)
}
```

| Тип | Поля |
|---|---|
| `SolveRequest` | `mode: baseline \| optimized \| insert_only`, `orders: Order[]`, `engineers: Engineer[]`, `engineer_states: EngineerState[]`, `already_used_engineer_ids: string[]`, `travel_matrix: TravelMatrix`, `fixed_routes: Route[]`, `protected_leg_ids: string[]`, `time_limit_ms: int64` |
| `SolveResult` | `routes: Route[]`, `unassigned: UnassignedOrder[]`, `termination: completed \| time_limit` |

Go-4 передаёт только ещё не начатые заявки со статусом `active`, `sent` или `en_route` и доступных инженеров. Каждому инженеру соответствует `EngineerState = {engineer_id, start_location_id, available_from, equipment_available}`. Матрица содержит все точки и необходимые профили. Подтверждённо выполненные, начатые и отменённые работы не передаются Go-1; их история остаётся у Go-4.

`equipment_available` — выдача на начало дня за вычетом потребностей всех фактически начатых работ этого инженера. Для начатой работы остаток не списывается повторно при объединении плана. `Order.service_sec` уже очищено от нормативной дороги: у аварии 4800 секунд; фактическая поездка учитывается по матрице один раз. Все заявки и инженеры относятся к одному `Snapshot.region_id`.

Каждая переданная заявка должна быть в маршруте либо в `unassigned`. `time_limit` — допустимый результат, не ошибка; для `insert_only` fallback обязан сохранить `fixed_routes` и вернуть новую заявку в `unassigned`, старые фиксированные визиты нельзя терять. `INVALID_INPUT` / `COMPUTATION_FAILED` прерывают расчёт. Геометрию в ответ Go-1 не добавляет. Правила назначения и приоритетов: [planner.md](planner.md).

## Команды

| Тип | Поля |
|---|---|
| `BuildPlanRequest` | `request_id`, `scenario_id`, `snapshot_revision: int64`, `expected_current_plan_id: string?` |
| `ReplanRequest` | `request_id`, `scenario_id`, `snapshot_revision: int64` — исходная ревизия до события, `base_plan_id`, `event: Event` |

Тело события определено в [общих типах](common.md). Для `Replan` сценарий, текущая ревизия и ревизия базового плана должны совпадать; `base_plan_id` должен быть текущим планом при сохранении.

`Build` и ручное редактирование инженеров используются до начала операционного дня. Если уже есть результат события (`current_plan.base_plan_id != null` или `as_of` после начала дня) либо хотя бы одна `Order.execution != null`, обычная пересборка возвращает `EVENT_CONFLICT`: дальнейшие изменения проходят через `Replan`, чтобы не потерять историю и расход оборудования. Начальная отменённая заявка без `execution` не мешает первому расчёту. До начала дня изменение инженера требует нового `Build` по новой ревизии.

## Обычное планирование

1. Прочитать точную ревизию снимка. Подготовить активные заявки и доступных инженеров; старт — офис и начало смены, `equipment_available=equipment_stock`. Начальные отмены исключить из назначения.
2. Получить матрицу для используемых транспортных профилей.
3. Вызвать базовый и оптимизированный расчёты на одинаковой задаче и матрице.
4. Проверить оба результата, получить геометрию оптимизированного плана и рассчитать метрики.
5. Вернуть `PlanResult`: полный план, `baseline_metrics`, исходный `target_snapshot`, `applied_event=null`, `base_plan_id=null`, `changes=[]`. `equipment_remaining` содержит стартовую выдачу всех инженеров, `completed_order_ids=[]`, `completed_count=0`.

`as_of` обычного плана — начало местного дня. Метод ничего не сохраняет; сохранением занимается Go-2.

## Перепланирование

1. Проверить событие: время не раньше `base_plan.as_of` и в пределах выбранного местного дня. Объекты принадлежат тому же сценарию; ID и ожидаемые версии корректны.
2. Определить положение инженеров по подтверждённым статусам исходного снимка и сохранённым поездкам. Сохранить фактическое прошлое; у бригады `en_route` рассчитать пройденную часть текущей поездки через `PositionAt`. Плановое `Visit.end_at` не означает, что работы закончены.
3. Применить событие к копии снимка, включая фактические времена и расход оборудования. При новой аварии или обычной заявке разрешить адрес через Go-3; `received_at=occurred_at`. Ошибка события или адреса не меняет текущие данные.
4. Сформировать стартовые состояния по правилам ниже. Сохранить завершённые работы, фактическую часть отменённых работ и `in_progress`. Не включать в новый расчёт инженера с незавершённой работой, для которой нет будущей оценки окончания.
5. Подготовить ещё не начатые заявки. Нижнюю границу окна во входе Go-1 поднять до `max(window.start, occurred_at, received_at)`, не изменяя обещанное окно в снимке. Если эта граница позже конца окна, оставить заявку неназначенной с `NO_FEASIBLE_SLOT`. Начало поездки также не раньше поступления заявки.
6. Для `ordinary_order_added` подготовить только будущую часть старого плана: передать её как `fixed_routes`, текущую защищённую поездку — в `protected_leg_ids`, а Go-1 вызвать с `mode=insert_only`. Старые будущие визиты фиксируются по инженеру, времени прибытия/начала/окончания и относительному порядку; разрешены только новая заявка в зазор и замена дорожных плеч. Если проверка Go-4 обнаруживает конфликт фиксированной части старого плана, не вызывать Go-1: вернуть `Issue(EXISTING_PLAN_CONFLICT)`, предупреждение и новую заявку в `unassigned` с `reason_code=NOT_ASSIGNED_BY_SOLVER` и объяснением; старый план не менять. `EXISTING_PLAN_CONFLICT` не использовать как `reason_code`. Ранее неназначенные заявки оставить у Go-4, без передачи в `Solve` и без вторичной оптимизации. Для аварии обычный режим перепланирования может перестроить оставшуюся часть дня, но начатая работа не прерывается: сначала завершается текущая заявка, затем выбирается подходящая бригада. Получить матрицу новых стартов, вызвать Go-1, объединить результат с сохранённой частью дня. Проверить будущие назначения по исходным клиентским окнам, квалификации, транспорту, оборудованию и сменам. Рассчитать метрики и изменения. Геометрию получать только для новых участков; сохранённую геометрию не перестраивать.
7. Вернуть `PlanResult` с `target_snapshot.revision = snapshot_revision + 1`, соответствующим `draft.snapshot_revision`, применённым событием, `base_plan_id` и `as_of=event.occurred_at`. `baseline_metrics=null`; сравнение с предыдущим планом доступно по `base_plan_id`.

## Факты, положение и доступность

- Статусы `sent`, `en_route`, `in_progress`, `completed` подтверждаются событиями диспетчера по информации бригады. В демонстрации эти же события можно подготовить заранее; пропуск планового времени не заменяет подтверждения.
- У инженера не более одной фактически текущей поездки или начатой работы. До первого выезда его точка — офис; после подтверждённого выполнения или отмены на месте — адрес последней работы. Неподтверждённые будущие поездки не включаются в пройденный пробег.
- При подтверждении `en_route` текущая поездка начинается в подтверждённый `departed_at` из фактической точки инженера; Go-4 рассчитывает её длительность и геометрию через Go-3. Между событиями положение в пути моделируется по этому участку. Если его расчётное окончание уже прошло, инженер считается у адреса и ожидающим подтверждения начала работы; выполнение не начинается автоматически.
- При следующем событии используется текущий участок базового плана. Пройденный фрагмент сохраняется, непройденный может измениться. Для точки события Go-4 создаёт стабильный ID в `target_snapshot.locations`; `PositionAt` вызывается только внутри интервала участка, за его концом берётся конечная точка.
- Для `in_progress` фактическое начало равно `execution.started_at`, положение — адрес заявки. При `expected_end_at > occurred_at` инженер доступен для будущих работ с этой оценки. Если оценки нет либо она истекла, будущих назначений этому инженеру нет, а `Plan.issues` содержит `EXECUTION_STATE_REQUIRED` с ID заявки: нужно подтвердить завершение либо обновить оценку. Остальные инженеры продолжают планироваться; это предупреждение, не ошибка всей команды.
- В сохранённом `Visit` начатой работы `end_at` — будущая оценка, а при её отсутствии или истечении — `as_of`, граница отображённого фактического времени. Это не подтверждение окончания. У `completed` используются подтверждённые `started_at` и `finished_at`; у отменённой после начала — фактический интервал до отмены. Перерасход времени относительно норматива сохраняется как факт и не исправляется задним числом; нарушения окна/смены отражаются в `issues` как `ACTUAL_CONSTRAINT_VIOLATION`, будущие работы всё равно проверяются строго.
- Остальным инженерам `available_from = max(occurred_at, shift.start)`. `available=false` исключает будущие назначения, но не удаляет историю или начатую работу.

Начатая работа не прерывается ради аварии. После её завершения подходящая бригада может быть направлена на аварию, а оставшийся маршрут перестроен. Для сетевой аварии ориентир реакции — 1–2 часа; это ориентир планирования, а не жёсткий SLA или минимальное ожидание. Обычная новая заявка вставляется в свободный интервал через `insert_only` и не перестраивает уже сформированные визиты.

## Семантика событий

- Новая авария: ID ещё не существует; `work_type=emergency`, `priority=urgent`, `service_sec=4800`, `status=active`, `execution=null`, `received_at=occurred_at`. Потребность в оборудовании и необходимые навыки обязательны, даже при максимальном приоритете. 100 минут не добавляются поверх дороги и не задают отдельный deadline от поступления.
- Новая обычная заявка: `Event.type=ordinary_order_added`, `payload={order: Order, location: LocationInput?}`, `work_type=connection|repair|additional`, `priority=normal`, `status=active`, `execution=null`, `received_at=occurred_at`. Go-4 передаёт её в `insert_only`; при отсутствии слота использует `NO_FEASIBLE_INSERTION`, при конфликте со старым будущим планом — `EXISTING_PLAN_CONFLICT`. Такую неназначенную заявку сохраняют для следующего аварийного пересчёта.
- `order_status_changed`: проверить переход по [common.md](common.md), совпадение `engineer_id` с текущим назначением и, после отправления, с `execution.engineer_id`. `sent` заполняет исполнителя; `en_route` — `departed_at`; `in_progress` — `started_at`; `completed` — `finished_at`. Времена берутся из `occurred_at`, идут по порядку; завершение строго позже начала. Начало работы не раньше фактического прибытия, поступления заявки и начала клиентского окна. Инженер с другой текущей поездкой/работой не может начать новую. Неверный переход — `EVENT_CONFLICT`.
- Первое `in_progress` проверяет наличие оборудования, фиксирует полную потребность как израсходованную через `started_at`. Повтор `in_progress` допускается для обновления `expected_end_at`, не меняет начало и не списывает оборудование снова. Переданная оценка должна быть позже события; `null` означает неизвестное окончание. Завершение подтверждает диспетчер, затем заявка попадает в `completed_order_ids` и больше не передаётся в `Solve`.
- Отмена `order_cancelled`: причины `client_refusal` или `cannot_perform`, допускается для любой незавершённой заявки, включая поездку и начатую работу. При отмене на месте сохраняются фактическая работа, дорога и расход; для ещё не начатой потребность освобождается. Завершённая или уже отменённая заявка — `EVENT_CONFLICT`.
- Недоступность инженера освобождает будущие назначения. Начатая работа сохраняется без автоматического завершения; её окончание или отмена подтверждаются отдельно. Если инженер в пути, сохраняется поездка до положения на момент события.
- При изменении исполнителя ещё не начатой отправленной заявки её текущее состояние сбрасывается в `active`, `execution=null`: требуется новая отправка. При перенаправлении в пути оставшаяся прежняя заявка также возвращается в `active`. Предыдущее отправление и пройденная дорога остаются в истории событий и маршрута; сведения о фактически начатых работах никогда не сбрасываются. Это правило актуальности маршрута, не подтверждение выполнения и не интеграция с внешней системой отправки.
- Изменение планового времени визита отражается в `changes`; клиенту об этом сообщает поддержка. Само клиентское окно снимка не расширяется. При проверке `ordinary_order_added` Go-4 проверяет наличие свободного зазора с учётом всех фиксированных визитов, дороги, окна, навыков, транспорта, оборудования и смены; при отсутствии зазора заявка остаётся неназначенной с `NO_FEASIBLE_INSERTION`.
- Заправка и очереди на АЗС не моделируются. Для пешего или велосипедного инженера нет обязательного норматива грузоподъёмности; 1–2 единицы оборудования — допустимое модельное допущение. Оборудование может отсутствовать: `equipment_required={}`. Временные окна фиксированы в базовой модели; гибкие окна допускаются только как отдельный эксперимент. Один CSV-файл — один регион, при этом города Москвы и Подмосковья внутри файла могут обслуживаться общими бригадами; лишние перегоны следует минимизировать.

## Проверка и изменения

- При разделении поездки Go-4 добавляет точку события с новым ID в `target_snapshot.locations`. Пройденный фрагмент получает отдельный ID, `end_at=occurred_at`, расстояние и геометрию из `PositionAt`; исходный участок в старом плане неизменяем. Времена и расстояния двух фрагментов исходной поездки в сумме равны исходным. Будущий фрагмент может быть заменён новым маршрутом, и его показатели уже могут отличаться.
- Проверить уникальность будущих назначений, навыки, транспорт, окна, поступление, смены, недорожные длительности, фактическое время поездок и остатки оборудования. Нарушение результата Go-1 — `INVALID_PLAN`, сохранение запрещено. Единственное исключение — заранее выявленный Go-4 конфликт старого фиксированного плана: он возвращается как `EXISTING_PLAN_CONFLICT` с предупреждением и новой неназначенной заявкой, а не как `INVALID_PLAN`. Подтверждённые факты не меняются ради соответствия прогнозу.
- Каждая корректная ещё не начатая заявка находится в будущем маршруте либо среди неназначенных. Начатая сохранена в маршруте. Завершённые перечислены в `completed_order_ids`, отменённые — в `cancelled_order_ids`; у них может оставаться история, но нет нового назначения. Новые ошибки данных и предупреждения остаются отдельно в `issues`.
- Метрики учитывают сохранённые и будущие участки без двойного счёта. При перепланировании `already_used_engineer_ids` строится из сохранённого прошлого. `equipment_remaining` вычисляется из целевого снимка для всех инженеров и содержит фактический остаток без вычета будущих резерваций.
- `changes.before/after` содержит исполнителя, позицию и времена. При смене исполнителя причина `reassigned`, при изменении времени/позиции — `rescheduled`; остальные причины соответствуют появлению/исчезновению назначения. Отмена отражается как `cancelled`, `after=null`, включая неназначенную заявку с `before=null`. Для подтверждения состояния причина `status_changed`, даже если назначение не изменилось; прежний и новый статус читаются из снимков двух планов. Подтверждённая работа остаётся в истории, а не превращается в неназначенную.

## Начало самостоятельной разработки

1. Подключить заглушки `PlanDataReader`, `GeoService` и `Planner` по сигнатурам выше. Общие структуры — из [common.md](common.md).
2. Использовать [backend_flow.json](examples/backend_flow.json): снимок, матрицу, вход / выход `Solve`, геометрию и ожидаемый `PlanResult`.
3. Собрать `Build`: проверить два результата на одной задаче, получить геометрию, рассчитать метрики и вернуть результат Go-2.
4. Затем реализовать события аварии, отмены, недоступности и подтверждения статуса. Проверить, что истечение планового времени не закрывает заявку, подтверждённое закрытие исключает её из `Solve`, авария без нужного оборудования остаётся неназначенной, а повтор завершения не расходует запас снова. Хранилище и API для этого запускать не требуется.

Go-4 использует тот же алгоритм Go-1 для обычного расчёта и событий; собственной реализации распределения здесь нет.
