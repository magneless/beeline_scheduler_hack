# Q&A 1 — сводка

Источник: [QA_raw.md](QA_raw.md).

## Извлечённые сведения

| Тема | Информация |
|---|---|
| Данные и оценка | Дополнительные датасеты не планируются. При оценке будет рассматриваться демонстрация того, как участники распределили предоставленные заявки. |
| Состав данных | Синтетические данные содержат заявки без назначенных бригад, для которых нужно построить маршруты. Контрольные данные показывают реальное распределение диспетчерами за конкретный день. |
| Контрольное распределение | Контрольные данные не являются эталоном качества. Число исполнителей и распределение в решении могут отличаться от исторического примера. |
| Недостающие данные | Команды могут самостоятельно генерировать отсутствующие характеристики. Демонстрация влияния квалификации исполнителей на маршруты будет оцениваться. |
| Список исполнителей | Колонка «Бригады» содержит исполнителей, которым были назначены заявки. Фактически доступных исполнителей может быть больше или меньше. |
| Бригада и инженер | Для этой задачи одна бригада соответствует одному человеку. Делить бригаду на отдельных инженеров не нужно. |
| Независимость регионов | Три региона рассматриваются как три независимых сценария с отдельными участками, офисами и исполнителями. Повторяющаяся фамилия в разных регионах, предположительно, возникла при обезличивании данных. |
| Начальная точка | Адрес офиса указан отдельной строкой ниже основной таблицы синтетического файла. У каждого региона свой офис и своя точка старта. |
| Модель компетенций | Навык определяется типом работ: локальная заявка, подключение или дозаказ. Исполнитель может выполнять один, два или все три типа; квалификации команды задают самостоятельно. |
| Независимость навыков | Навыки не связаны напрямую с оборудованием и типом транспорта. |
| Нормативы | Представитель постановщика сообщил, что предоставит таблицу нормативов длительности работ по типам заявок. |
| Состав времени дороги | Парковку, пропускной режим и подъём в квартиру отдельно учитывать необязательно: их можно включить в общее время дороги. При бронировании на месяц-два вперёд используется среднее время передвижения. |
| Приоритеты типов работ | Изначально приоритет не задан; равный приоритет аварийных и обычных заявок не считается ошибкой. В качестве варианта можно сделать новые подключения наиболее приоритетными; выделение приоритета аварий или подключений оценивается как плюс. |
| Аварийные заявки | Аварию следует планировать как можно раньше в пределах заданного интервала; в ответе упомянут интервал на целый день. Под выполнение такой заявки должно быть зарезервировано время. |
| Выезды по заявкам | Все строки контрольного распределения по умолчанию предполагают выезд бригады, включая мониторинг и информацию. |
| Транспорт и маршрутизация | Отсутствующий тип транспорта можно задать синтетически. Время маршрута должно учитывать транспорт, поскольку автомобиль и пешеход передвигаются по-разному; пробег считается по дорогам. |
| Общественный транспорт | Учёт общественного транспорта назван интересным вариантом для демонстрации. Модель транспорта и доли его типов команда может определить самостоятельно. |
| Геокодирование и карты | Разрешены открытые геокодеры и сервисы OpenStreetMap, Яндекс и 2GIS. Для прототипа допускаются открытые источники и триальные версии; покупка платного API не является условием участия. |
| Клиентское окно | Окно в данных — обещанный клиенту интервал прибытия. Приехать раньше и ждать можно; начинать работу до начала окна нельзя. |
| Опоздание | Эксперт ответил, что опоздание допустимо, и привёл пример: окно 10:00–12:00, прибытие в 10:30. В том же ответе сказано, что нормативы помогут регулировать опоздание. |
| Начало и завершение работ | Обязательство перед клиентом — начать работу в установленный срок. Завершение в срок желательно, но жёсткого требования к окончанию работ нет. |
| Часовые пояса | Время в датасете указано по Москве. При выдаче слотов для других регионов желательно учитывать местное время; в качестве примеров названы Владивосток и Москва. |
| Перерывы | Обеденные и технические перерывы в исходной постановке не учитывались. Их поддержка необязательна и оценивается как дополнительный плюс. |
| Статусы заявки | В ответе сказано планировать все заявки из файла. Заявки, отменённые клиентом до выезда инженера, распределять не нужно. |
| Переполнение расписания | Большое число заявок у одной бригады в одном окне может отражать реальный овербукинг. Алгоритм должен показывать заявки, которые не помещаются по времени; в реальности старший инженер договаривается с клиентом о переносе. |
| Базовый алгоритм | На вопрос о baseline эксперт ответил, что базового алгоритма как такового нет, а контрольные данные не являются эталоном. Качество оценивается по маршрутам, количеству исполнителей и закрытых заявок. |
| Перепланирование | Ради аварии можно развернуть инженера в пути или снять бригаду с заявки. Авария может сдвигать или отменять обычные визиты. |
| Переносы и отмены | Сдвигать клиентское окно нельзя. Заявку, которая не помещается, можно перенести на следующий день; просто отказывать в ней нельзя. Отмена возможна при отказе клиента, в том числе по прибытии инженера. |
| Горизонт планирования | Предоставленные заявки относятся к одному дню. В реальном процессе горизонт может достигать месяца, автоматическое распределение обычно выполняется на следующий день, а необеспеченные ресурсами заявки распределяются вручную. |
| Оборудование | Оборудование условно разделяется на роутеры и ТВ-приставки; инженер получает его в офисе в начале дня. Различия гигабитного и обычного подключения учитывать не требуется. |
| Приоритет метрик | При конфликте критериев важнее выполнить больше заявок, затем задействовать меньше исполнителей. Оптимальность маршрутов также учитывается при оценке решения. |
| Независимость заявок | Заявки считаются независимыми. Закрытие аварии не означает автоматического закрытия других заявок. |
| Пользователь и интерфейс | Пользователь прототипа — диспетчер. Отдельный экран или мобильное приложение для инженера не требуется; ему достаточно получить маршрут. |
| Объяснения решений | Длинные текстовые объяснения алгоритма диспетчеру не нужны. Достаточно эффективной работы алгоритма. |
| Развёртывание | Сервис можно запускать локально или в облаке; главное, чтобы он работал. |
| Технологии и ИИ | Стек не ограничен. LLM и другие ИИ-инструменты необязательны; допустимы классические алгоритмы VRP. Оцениваются результат и эффективность логики распределения. |
| Документация | Требования к документации определены в правилах хакатона. Представитель постановщика подчеркнул значимость бизнес-функциональности и работы алгоритма. |
